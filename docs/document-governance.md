# 문서·코드·앱의 일치 규칙

2026-10-25 사용자 요구: **문서, 소스코드, 앱의 기능은 모순 없이 서로를 설명할 수 있어야 한다.** 이 문서는 작업 방법을 정한다. 제품 요구의 입구는 [정본](canonical.md), 게임 의도는 [기획](game-design.md)다.

## 위계와 역할

| 단계 | 소유 문서/산출물 | 답해야 할 질문 |
|---|---|---|
| 최상위 | 최신 사용자 지시·제공 원본 | 무엇을 보존하고 무엇을 바꾸도록 승인했는가? |
| 1. 제품 요구 | game-design, restoration-contract | 플레이어에게 어떤 경험·규칙·화면을 제공하는가? |
| 2. 구현 설계 | design, 좌표·렌더·수치·실행 정책 | 그 요구를 어떤 구조·좌표·연산·수명으로 구현하는가? |
| 3. 구현과 검사 | Sources, iOS 구성, Tests | 실제 어느 경로가 실행되며 어떤 입력으로 확인하는가? |
| 4. 실행 증거 | current-status, 설치/계측/사용자 관측 기록 | 어느 소스·앱·기기·조건에서 무엇을 확인했는가? |

canonical은 이 위계를 안내하는 색인과 보존 규칙이다. current-status는 실제 상태를 소유하며 제품 규칙을 임의 변경하지 않는다. 보고 사이트와 공개 회고는 위 문서의 파생본이다. 보고서의 문장만으로 설계·코드가 바뀌지 않는다.

상위 요구는 아래로 반영한다. 아래 단계의 실패·관측은 위 요구의 해석을 재검토하는 근거로 올린다. 코드가 다르다는 이유로 문서를 코드에 맞춰 정당화하거나, 오래된 문서에 맞추려고 정상 앱을 바꾸지 않는다. 최신 승인·원본·재현 증거로 어느 쪽을 고칠지 결정한다. 원본 보존과 승인된 확장의 적용 범위를 함께 기록한다.

## 업무별 진입

HeavyMach 요청이면 루트에서 시작해도 HeavyMach/AGENTS를 읽는다. 공통 문서와 업무별 필수 문서·코드·검사는 [문서 연결표](document-map.json)가 소유한다. 작업자의 실제 읽기를 명령이 대신했다고 보고하지 않는다.

```sh
python3 HeavyMach/tools/document_contract.py plan --task input
python3 HeavyMach/tools/document_contract.py plan --files HeavyMach/Sources/Core/Combat.cpp
python3 HeavyMach/tools/document_contract.py check
```

업무 종류: planning(기획/규칙), input(입력/회전), rendering(그래픽/아트), menus(메뉴/전환), combat(무기/적/수치), runtime(음향/저장/생명주기), validation(빌드/실기기), documentation(문서/보고). 여러 영역이면 합집합을 읽는다. 파일 경로로 업무를 찾지 못하면 관련 요구를 직접 분류하고 연결표를 보완한다. 상위 사용자 지시를 단어 일치로 자동 해석하지 않는다.

## 변경 전후의 필수 대조

1. **요구 확인:** 기획의 요구 ID와 최신 사용자 지시를 고른다. 현행 동작, 승인됐지만 미구현인 요구, 조사 후보를 구분한다.
2. **영향 확인:** 연결표의 정책·코드·검사를 읽고 실제 호출 경로를 대조한다. 한 파일을 고쳐도 입력→규칙→표시→저장 중 영향을 받는 범위를 찾는다.
3. **변경 방향 결정:** 기획 변경이면 제품 요구→설계/정책→코드/검사 순으로 반영한다. 구현 오류면 요구를 보존하고 코드를 고친다. 문서 오류면 증거로 문서를 고치고 과거 기록은 이력으로 남긴다.
4. **실행 확인:** 관련 검사를 실행한다. 앱 기능 변경은 실제 해당 앱 경로까지 확인하고 빌드·설치·직접 조작·자동 검사·사용자 관측을 분리한다. 유효한 기존 증거는 재사용하되 소스나 조건이 달라지면 적용 범위를 다시 판단한다.
5. **일치 확인:** 요구의 각 조건을 소비 코드와 검사/앱 관측에 연결한다. ‘미구현’, ‘미검사’, ‘실패’가 있으면 그대로 표시한다. 문서만 완료로 바꾸지 않는다.
6. **동시 갱신:** 기획/설계가 바뀐 경우 영향 문서와 코드·검사를 같은 변경에 포함한다. 관련 문서 수정이 필요 없다면 유지되는 규칙과 근거를 변경 기록에 적는다. 최신 실행 상태는 current-status, 후속 일은 TODO, 보고는 기존 Sites에 반영한다.

필수 기록은 기존 작업 보고에 `요구 ID / 변경 전후 / 정책·소비 코드 / 실행 근거 / 남은 범위`로 남긴다. 별도 승인 장부나 작업 허가 절차를 추가하지 않는다.

## 상태와 출처

- **현행:** 현재 제품이 구현한 계약. 구현 파일을 연결한다.
- **승인·미구현:** 사용자가 지시했지만 아직 앱에 없는 기능. 구현 완료와 구분한다.
- **검토:** 조사·후보이며 채택된 요구로 바꾸지 않는다.
- **증거/이력:** 당시 입력·결과·실패 기록. 지금의 상태와 다르면 날짜·대체 문서를 표시하고 원시 결과는 보존한다.

규범 문서와 절차 목록은 document-map의 `current_documents`에 둔다. 그 외 docs의 조사·회고·과거 구현 보고는 증거/이력이며 현행 계약을 덮어쓰지 않는다. 현행 문서를 새로 만들면 목록과 업무 연결을 함께 갱신한다. 과거 숫자·실패·사용자 관측을 삭제해서 일치한 것처럼 만들지 않는다.

## 검사 도구가 확인하는 것

`check`는 연결표의 문서·코드 패턴·검사 파일 존재와 현행 문서의 로컬 링크를 확인한다. `plan`은 읽을 문서와 검토할 소스·검사를 출력한다. 둘 다 앱 동작이나 문장 의미의 일치를 증명하지 않는다. 의미 대조와 실제 앱 검사는 작업자가 수행한다. 현재 Git 훅은 비밀 검사이며 문서 검사 도구를 자동 실행하지 않는다. 읽기·대조·check 실행은 AGENTS의 작업 규칙으로 적용한다.

일치 판정에는 **요구 → 정책 → 코드 → 검사/앱 증거**가 모두 필요하다. 반대로 앱의 특정 행동을 보고도 해당 코드와 요구를 찾아 설명할 수 있어야 한다. 연결이 없거나 설명이 충돌하면 그 범위를 미확인으로 남기고 완료 보고 전에 해소한다.
