## 현재 코드에서 확인한 것

현재 표시 경로는 480×320 전체 장면을 화면에 비율 맞춤으로 넣는다. 넓은 가로 화면에는 좌우 검정 여백이 생긴다. 화면 높이보다 크게 확대하여 원본 장면의 좌우를 잘라내는 계산은 없다. 다만 이번 사용자 보고 장면의 캡처를 새로 측정하지 않았으므로 사용자가 본 잘림을 검정 여백 하나로 확정하지 않는다.

| 구분 | 확인한 사실·확인 방법 |
|---|---|
| 원본 장면 자체의 잘림 | 논리 화면 가장자리의 물체·HUD가 사라지는 문제다. 같은 시점의 논리 버퍼와 최종 폰 캡처를 비교하여 확인한다. 아직 새 재현은 하지 않았다. |
| 좌우 여백 | `Viewport::drawable`이 3:2 비율을 유지하고 남는 폭을 가운데 정렬한다. `HMGLRenderer`는 drawable 전체를 검정으로 지운 후 이 영역에 표시한다. 코드로 확인했다. |
| 시야 폭 제한 | 월드가 480 논리 단위의 화면에 투영된다. 여백에는 추가 지형·적을 그리지 않는다. 코드로 확인했다. |
| 기기 외곽 가림 | 현재 장면 배치는 safe area를 제외하지 않는다. 화면 모서리·카메라 영역과 실제 콘텐츠의 겹침은 양쪽 가로 방향에서 별도로 측정해야 한다. |

코드 근거: `Sources/Core/Viewport.hpp:11`, `Sources/iOS/HMGameView.mm:482`, `Sources/iOS/HMGLRenderer.mm:197`. 예를 들어 기존 검사에 쓰인 912×420 point 화면은 게임 폭630 point, 좌우 여백141 point다. 이는 특정 폰의 최신 실측치가 아니라 `Tests/iOS/HMFramePerformanceTests.mm`의 `testProductionTimerAndFullScreenTouchViewport` 입력값이다.

포팅판의 `iOS Proj/HeavyMachRecovery/compat-source/fresh-port/20-touchHLE-src/touchHLE/src/window.rs:3210`도 iOS 기본 경로에서 guest 비율에 맞는 viewport를 계산한다. 같은 파일에는 `--fill-screen`/`--logical-size`를 위한 별도 사용자 지정 guest 크기 분기가 있다. 그것이 HeavyMach 원본의 고정 좌표·투영·게임 판정을 자동으로 넓혀 준다는 근거는 없다. 포팅판의 옵션만 복사하거나 최종 표시 quad만 늘리는 것으로 이 요구를 충족하지 않는다. 현재 호환 비교 기록은 [직접 비교](compat-source-comparison-20261024.md)에 있다.

## 권장 화면 방식

게임 플레이에 고정 높이·가변 폭 캔버스를 도입한다. 높이는 320 논리 단위를 유지한다. 가로 폭은 실제 게임 영역의 비율에서 계산한다. 에셋의 크기·비율·UV·색·필터는 보존한다. 넓어진 좌우에는 기존 월드에 있는 물체를 더 그린다.

가로 drawable 폭을 `Dw`, 높이를 `Dh`라 하면 넓은 화면에서 `H=320`, `W=320×Dw/Dh`다. 예를 들어16:9는 약568.89,19.5:9는 약693.33이다. 이 수치는 계산 예시다. 실제 폰에서는 할당된 drawable 크기를 읽는다. 3:2에서는 정확히480으로 복귀한다. 3:2보다 좁은 영역은 이번 확장 대상에서 원본 화면의 fit 표시를 유지하며, 세로 방향 확대는 별도 과제로 둔다.

논리 `W`는 실수로 유지하고 장면 버퍼 폭은 `ceil(W)` 픽셀로 할당한다. 투영 폭과 최종 drawable 비율은 동일한 실수 `W`를 사용한다. 정수 버퍼 반올림을 게임 좌표에 되돌려 누적 오차를 만들지 않는다. HUD와 터치도 동일한 프레임의 치수 객체를 사용한다. resize 때만 버퍼를 다시 할당하고 매프레임 재생성하지 않는다.

원본 카메라를 보존하는 비교 단계에서는 기존 화면 좌표에 `extra=(W−480)/2`를 더한다. 원본 좌표240이 새 캔버스 중심 `W/2`가 된다. 따라서 탱크와 지형의 크기는 같고 원본480 영역의 양쪽이 열리는 방식이다. 단순 확대·가로 늘이기는 추가 월드 정보를 만들지 않으므로 사용하지 않는다.

## 렌더·HUD·입력 변경 범위

1. `HMGLRenderer.mm:48`, `:70`, `:73`, `:191`, `:216`, `:232`의 장면 할당·viewport·projection·copy·복원·readback 크기를 모두 같은 치수에서 얻는다. 480×320과 확장 모드가 같은 ES1.1 경로를 사용한다. 원본 텍스처 필터·blend·순서는 유지한다.
2. `HMGameView.mm`의 장면 제출 사각형과 논리 프레임 클립을 가변화한다. UIKit 레이아웃에서 게임 tick을 추가 실행하지 않는다. CPU 비교 렌더도 새 크기를 받게 하거나 명시적으로 원본480 검사 전용으로 제한한다. 어느 경로인지 검사 결과에 적는다.
3. HUD는 우선 기존 480×320 묶음을 중앙에 같은 크기로 배치한다. `GameUI_Top/Btm`을 가로로 늘리지 않는다. 전체 캔버스의 좌우는 월드가 채운다. 메뉴·부스터·무기 버튼을 외곽에 이동하는 조작 개선은 별도 배치 변경으로 다룬다.
4. HUD의 모든 자식과 hit 영역에 같은 이동량을 적용한다. `HMGameHUD.mm:164`의 배경만 옮기고 버튼·게이지·숫자를 남기지 않는다. 메뉴·업그레이드 패널의 원본 퇴장 위치660/720은 넓은 캔버스에 노출될 수 있다(`:189`–`192`). 패널별 클립 영역과 퇴장 완료 조건을 함께 처리한다.
5. 월드 터치는 전체 캔버스에서 허용한다. `canvasX=(pointX−originX)/scaleX`, `canvasY=320−(pointY−originY)/scaleY`를 계산한다. 중앙HUD는 `hudX=canvasX−extra`로 원본 hit 규칙에 전달한다. 월드 터치는 같은 표시 카메라를 역변환하여 플레이어 조준점에 전달한다. `Player.cpp:86`의100/60 사격·대시 기준은 보존한다.
6. 스테이지 결과·로딩·일시정지·업그레이드가 열리면 캔버스 전체에서 월드 터치를 막는다. 원본480 영역 밖을 눌러 모달 뒤로 발사되지 않아야 한다. 터치 종료·취소는 영역 밖에서도 발사를 해제한다. 다중 터치의 버튼/월드 소유권을 유지한다.

게임 월드는 drawable 전체에 표시하되 버튼·정보·중앙 모달은 실제 safe area 안에서 보여야 한다. 양쪽 가로 방향의 safe area가 다를 수 있으므로 고정 좌우 여백값을 쓰지 않는다. 중앙480 HUD가 안전 영역에 들어가는지 먼저 계산한다. 들어가지 않으면 HUD만 안전 영역에 맞춰 배치·크기를 조정하고 월드의 시야·크기는 유지한다. 그 경우 시각 배치와 hit 변환을 함께 검사한다. 카메라 영역 뒤에 월드가 이어지는 것은 전체 캔버스 정책의 결과이므로 그 위치에 필수 조작을 두지 않는다.

## 성능과 발열 영향

장면 버퍼와 복사 텍스처가 모두 RGBA8이면 논리 화면 두 장의 단순 픽셀 용량은 `8×ceil(W)×320` 바이트다. 원본 480은 1,228,800바이트, 폭 694는 1,776,640바이트로 547,840바이트 증가한다. 드라이버 정렬·drawable·기타 자원은 포함하지 않은 계산값이다. 장면 픽셀 수는 약 1.45배가 되지만 전체 프레임 비용이 1.45배라는 뜻은 아니다.

넓어진 영역의 지형·적·효과 때문에 draw 수와 알파 중첩도 증가한다. 실제 GPU 사용·표시 지연·메모리·열 상태를 재측정한다. 기존 Air 기록의 Serious 열 상태를 정상 기준으로 고정하지 않는다. 같은 충전·밝기·주변 조건에서 원본 480과 확장 모드를 번갈아 검사하고 냉각 상태를 기록한다. 시뮬레이터는 좌표·경계·자원 누수 검증에 사용하며 물리폰의 발열·GPU 비용을 대신했다고 보고하지 않는다.

기존 원본 텍스처와 자원 범위를 재사용하고, 가려진 지형·효과의 불필요한 제출을 줄인다. 버퍼는 resize 때만 갱신한다. 성능 문제를 숨기려고 게임 tick·데미지·발사 빈도를 바꾸지 않는다. 발열 정책은 별도 사용성 과제의 측정·대책과 함께 적용한다.

## 접히는 화면의 후속 범위

사용자가 제안한 위쪽 게임/아래쪽 조작 배치는 후속 과제다. 아직 특정 접힘 기기의 화면·자세 API나 실제 지원을 확인하지 않았다. 이번 치수 객체가 나중에 전체 디바이스 대신 상단 게임 영역을 받을 수 있도록 설계하되 현재 앱에 가상의 접힘 감지나 하단 패널을 넣지 않는다. 해당 기기의 실제 두 영역 크기와 safe area가 확인되면 원본 게임·HUD와 하단 조작부의 입력 소유권을 나누어 검증한다.

최초 계획 당시에는 구현·실기기 검사가 없었다. 현재 구현·검사와 설치 상태는 상단 및 current-status의 최신 기록을 따른다.
