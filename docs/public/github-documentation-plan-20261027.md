## 2. README에서 읽는 순서

1. **HeavyMach와 개발 동기:** 어떤 게임인지, 왜 다시 만들었는지를 짧게 적고 개발자의 변 전문으로 연결한다.
2. **현재 플레이 화면:** 01 자동조준 대표 화면을 크게 배치한다. 조작·무기·성장·클리어·추가 항공기 설명에 나머지 7장을 넣는다.
3. **플랫폼과 조작:** iPhone·iPad·native Mac, 터치·틸트·키보드, 일반 앱과 치트 앱의 차이를 표로 설명한다.
4. **개발 상태:** 개발 완료·개발 중·남은 과제와 실제 검증 범위를 보여준다. 현재 소스 버전과 설치·검사 기준을 함께 표시한다.
5. **직접 빌드하고 실행하기:** 준비 환경과 최소 실행 순서를 제공하고 플랫폼별 설치 문서로 연결한다.
6. **트러블슈팅:** 저장·렌더링·시간 진행·입력·화면 확장 등 주요 사건을 요약하고 전문으로 연결한다.
7. **사용자가 기획한 추가 기능:** 요구 이유, 구체적인 동작, 구현·검사 상태를 보여준다.
8. **구조와 개발 과정:** 공용 모듈, 그래픽·음향·저장 구조, 단계별 개발 순서, 사용한 도구·스킬을 연결한다.
9. **검증·버전·후속 작업:** 기기별 결과, 태그·롤백 방법, 남은 과제를 연결한다.
10. **제작자와 자원:** 원작 제작자, 추가 작업, 사용 라이브러리와 자원 출처를 정리한다.

README에 각 주제의 요약과 링크를 모두 둔다. 긴 사건 설명과 명령·검사표는 상세 문서에 둔다.

## 6. 완료·진행·남은 과제 표시

현행 상태표의 열은 `항목 / 개발 상태 / 실제 동작 / 확인한 플랫폼·조건 / 버전·근거 / 남은 일`로 정한다.

- **개발 완료:** 코드에 반영된 기능. 확인한 기기·검사와 남은 검증을 같은 행에 적는다.
- **개발 중:** 현재 수정 중인 코드·에셋·문서와 작업 브랜치.
- **남은 과제:** 연구 대기·계획 완료·미구현을 구체적으로 표시한다.
- **검증 잔여:** 성능 기준 실패, 장시간 발열, 추가 적 난도 등 후속 검사.

자동조준·신규 항공기·Apple 공용 모듈·전체 화면 도어는 구현됐다. HUD 편집·튜토리얼·상태 안내·아이콘·Android는 남은 과제다. 현재 작업은 GitHub 문서 정리다. 상세 상태는 `current-status.md`와 `usability-todo.md`에 있다.

## 9. 자동조준: 의도·목표·세부 구현

사용자는 아머드 코어6와 에이스 컴뱃7·8을 참고작으로 지정하고, 표적 선택·추적·전환과 포신 자동 조정을 요구했다.

**사용자가 지정한 목표**

- 무기 특성과 탄도를 계산해 표적을 향한 포신 각도를 자동 조정한다. 탱크 이동·점프에 따라 달라지는 발사 위치를 반영한다.
- 처음에는 가장 가까운 전방 적을 선택한다. 화면 밖으로 나가도 유지하고, 죽거나 탱크 뒤로 넘어가면 다른 적을 선택한다. 적이 없으면 표준 포신 각도로 돌아간다.
- 별도 버튼으로 다른 표적을 선택한다. 기존 터치 조준·발사와 자동조준을 ON/OFF로 전환하고, 자동 모드에서는 별도 발사 버튼을 사용한다.
- 버튼은 원작 HUD의 질감·색·배치에 맞춘다. 표적에는 모서리·사선·LOCKED 같은 상태 표지를 표시한다.

최초 요구에는 ‘발사 시점에 반드시 명중할 수 있는 조준’이 있었다. 이후 사용자는 탄속·분산·비행 경로까지 바꾸던 C 보정을 삭제하라고 지시했다. 최종 구현은 표적 선택과 포신 조정을 수행하며 원래 탄환 규칙을 유지한다. 탄환의 분산과 발사 후 적의 움직임에 따라 빗나갈 수 있다.

**실제로 구현한 방법**

| 부분 | 구현 내용 | 코드 |
|---|---|---|
| 표적 선택 | 살아 있는 적 중 월드 X가 탱크보다 큰 적을 고른다. 거리 제곱으로 비교하고 선택 후 유효한 동안 유지한다. 표적 전환은 거리순 후보를 사용한다. | `GameSession.cpp`: `findAimTarget`, `nearestAimTarget`, `cycleAimTarget` |
| 적 식별 | 스테이지 내에서 증가하는 정수 ID를 사용한다. 스테이지 시작 때 적 목록과 선택 ID를 함께 초기화한다. | `GameSession.cpp`: `nextID`, `start` |
| 탄도 예측 | 원래의 tick 단위 중력·위치 갱신 순서, 무기 속도·수명과 적의 직전 이동량을 사용한다. 최대 600 tick 범위에서 도달 후보를 찾는다. | `AutoAim.hpp`: `interceptionVelocity`, `solveAim` |
| 포구·차폐 | 차체와 포신에서 포구 위치를 다시 계산한다. 낮은 탄도가 지형에 막히면 높은 탄도를 검사한다. 공중 지원 무기는 별도 시작점을 반영한다. | `GameSession.cpp`: `updateAutoAim`, `aimPath`, `clearAimPath` |
| 사격 | 기존 탄환 생성·충돌·피해 처리를 사용한다. 생성된 탄환은 원래 탄속·분산으로 날아간다. 탄환의 표적 ID는 화면 밖 충돌과 검사 집계에 사용한다. | `GameSession.cpp`: `spawnBullet`, `Combat.cpp` |
| 입력·표시 | A 토글, 표적 전환, 발사 버튼을 HUD에 연결한다. 전환 시 발사 유지 입력을 정리하고 버튼 그림과 터치 영역을 함께 배치한다. | `HMGameView.mm`, `HMGameHUD.mm`, 공용 입력 코드 |

플레이어는 자동조준을 켜서 표적 추적과 포신 조정을 맡기고, 이동·점프·무기 선택·발사를 직접 조작한다. 자동조준을 끄면 기존 터치 조준·발사로 돌아간다.

`Tests/AutoAimTests.cpp`와 `Tests/Apple/HMAppleInputTests.mm`에서 표적·탄도·입력을 검사했다. 수동 사격 25,200프레임 기록은 자동조준 추가 전과 같았다. 화면 밖·차폐·대상 없음 상태를 더 잘 알리는 UI는 남은 과제다.

## 10. VTOL 3종: 의도·목표·세부 구현

사용자는 야크·해리어·F35 수직이착륙기를 기존 헬기와 같은 공중 적으로 추가하도록 지시했다. 기존 적 배치에 끼워 넣되 대체하지 않고, 수량은 미션별 헬기 수를 참고하게 했다. 실물과 다른 초기 시안은 다시 그리게 했고, 최종 길이·높이·외곽선·후방 불꽃 조건도 지정했다.

세 기체는 기존 캠페인에 추가됐으며, 아래와 같이 무장과 수치가 다르다.

| 기체 | 실제 채택한 형상 | 기존 수치·무장 재사용 | 표시 길이 |
|---|---|---|---|
| 야크 | Yak-141 | Heli004의 HP210·EXP10, 단발 미사일 `E_Wpn_ASM` | 112 |
| 해리어 | Harrier GR3 | Heli008의 HP400·EXP25, 2발 기관포 `E_Boss_Wpn_01` | 108 |
| F35 | F35B | E0604의 HP900·EXP60, 2발 미사일 `E_0604_Wpn` | 116 |

사용자는 세 기종과 기존 무장 재사용을 지정했고, 정확한 참조 유닛·무기 ID·수치는 구현안에서 정했다.

`VTOL.cpp`는 로드한 데이터에 새 정의와 배치를 추가한다. 원래 적 1,182항목의 순서·좌표를 유지하고 14개 서브미션에 113대(야크30·해리어41·F35B42)를 추가했다. 기존 적 사이의 월드 X 간격을 후보로 삼고, 맵 양끝·보스 주변을 피하며 지형 높이를 반영한다.

기존 헬기 이동을 사용하면서 수평·수직 속도로 기체 기울기를 계산한다. 같은 회전을 그림·발사점·피격 범위·후방 배기에 적용한다. 표시 길이는 Heli001보다 길고 Heli006보다 짧게 맞추며 높이도 비례 조정했다. 그림은 로드할 때 게임 표시 크기로 한 번 축소한 뒤 재사용한다.

실물 형상과 게임 화풍을 참조해 시안을 만들었다. 사용자 선택 후 외곽선·크기·불꽃을 수정하고, 게임에서 기존 헬기와 나란히 비교했다. `Tests/VTOLTests.cpp`에서 기존 스폰·추가 수량·이동·발사·피격을 검사했다. 추가 적을 포함한 전체 캠페인 난도 검사는 남아 있다.

## 11. 전투기 3종: 의도·목표·세부 구현

사용자는 럭스루나에 편대 도색의 F-22·Su-57·MiG-31, 금색 조종석, 더 높은 내구력과 빠른 미사일, 보스전과 직전 구간의 증원을 지정했다. 보스전 순서에 따라 수를 늘리되 최대 8대로 제한했다. 보스전과 그 직전 구간에 새 편대가 등장한다. 추가된 적을 포함한 전체 캠페인 난도 검사는 남아 있다.

| 사용자 목표 | 구현 |
|---|---|
| 가장 강한 일반 헬기의 1.7배 내구력 | 일반 헬기 최대 HP450을 읽어 세 기체에 HP765 적용 |
| 기존 미사일 재사용·비행 속도25% 증가 | 기존 정의를 신규 무기 ID로 복사하고 속도160→200. 기존 무기 정의 유지 |
| 단발3연사·2발씩3묶음 | F-22·Su-57은3발, MiG-31은 총6발. 기존 무기 갱신에 묶음 크기·대기 추가 |
| 연사속도 후속 조정 | 최초25% 증가에서10% 증가로 변경. 발사·AI 대기 간격을1.1로 나눔 |
| 보스전2/4/6/8대, 이후 최대8대 | 실제 대형 보스전7곳에 총44대. 중간보스 플래그만으로 판단하지 않음 |
| 보스전 직전 마지막 구간4대 | 해당7개 맵의 끝800단위 앞 진입을 조건으로 총28대 추가 |
| 갑작스러운 등장 수정 | 기체 전체를 화면 오른쪽 밖에 생성하고 이동해 진입. 진입 중 공격하지 않음 |

`Fighters.cpp`는 기체·무기 정의와14개 증원표를 소유한다. `GameSession.cpp`는 보스의 실제 전투 활성 또는 마지막 구간 진입을 확인해 한 번만 생성한다. `Combat.cpp`는 새 묶음 연사 필드를 처리한다. 회전·발사점·배기는 VTOL의 공통 처리를 사용한다. 기존 스폰·보스 수·클리어 규칙은 유지한다.

실물 기체의 형상, 편대 도색과 게임 질감을 참조해 그림을 만들고 조종석 유리를 금색으로 편집했다. `Tests/FightersTests.cpp`에서 수치·발사 시각·증원 조건·기존 데이터를 검사했고 iPhone·iPad에 설치했다. 사용자 플레이 후 갑작스러운 등장을 화면 밖 비행 진입으로 바꾸고 연사속도 증가율을10%로 낮췄다.

## 12. 워크스페이스·모듈화: 기술적 배경과 판단

사용자는 Apple 플랫폼을 하나의 workspace 아래 여러 project로 관리하고, 공용 코드와 에셋을 모듈로 만들어 앱에서 사용하도록 지시했다. iPad는 터치·틸트·키보드를 함께 지원하고 Mac은 Catalyst 없이 native 앱으로 만들도록 했다.

**이 프로젝트에 타당한 이유**

전투·이동·무기·미션·저장은 플랫폼이 달라도 같은 게임 규칙이다. 이를 앱별로 복사하면 버그 수정과 수치 변경을 여러 벌에 반영해야 하며, 어느 한쪽만 달라질 수 있다. 공용 코어 한 벌을 각 플랫폼에서 빌드하면 수정 위치와 검사 기준을 공유할 수 있다. 이미지·음향·맵도 한 자원 구성으로 관리하면 플랫폼별 누락과 버전 차이를 줄일 수 있다.

반면 iPhone·iPad의 UIKit 창·터치·센서와 Mac의 AppKit 창·메뉴·입력은 OS 연결이 다르다. 이 차이를 플랫폼 연결부에 두면 같은 게임 코어를 사용하면서 각 기기의 입력과 화면을 처리할 수 있다.

Apple은 workspace를 관련 프로젝트와 공용 프레임워크를 함께 관리하는 컨테이너로 설명하며 프로젝트 사이의 빌드 의존 관계를 지원한다. 이 프로젝트의 앱과 공용 모듈 구성이 그 용도에 맞는다. [Apple: 여러 프로젝트와 의존 관계](https://developer.apple.com/documentation/xcode/managing-multiple-projects-and-their-dependencies).

**실제 구성**

```text
HeavyMach.xcworkspace
├─ Modules/HeavyMachModules.xcodeproj
│  ├─ HeavyMachCore / HeavyMachValidationCore
│  ├─ HeavyMachAppleRuntime / HeavyMachValidationRuntime
│  └─ HeavyMachAssets.bundle
├─ iOS/HeavyMachRestored.xcodeproj     — iPhone·iPad
└─ macOS/HeavyMachMac.xcodeproj        — native Mac
```

| 구성 | 실제 책임 |
|---|---|
| workspace | 세 프로젝트를 한곳에서 열고 앱·프레임워크·번들의 빌드 관계 관리 |
| C++20 코어 | `Sources/Core` 한 벌을 iOS·macOS용 정적 프레임워크로 각각 빌드 |
| Apple 실행 코드 | 공통 Objective-C++ 코드와 `HMPlatform`·`HMGLPlatform`으로 OS별 창·입력·그래픽 컨텍스트 연결 |
| 자원 번들 | 이미지·음향·맵·추가 에셋을 한 구성에서 가져와 각 앱에 포함 |
| 일반·치트 분리 | 같은 소스에서 `HM_VALIDATION=0/1`로 각각 빌드. 앱과 코어의 설정을 맞추고 저장도 분리 |
| 앱 프로젝트 | iPhone·iPad는 같은 iOS target을 사용하고 Mac은 별도 AppKit 실행 진입점을 사용 |

정적 framework와 자원 bundle을 사용한다. `Sources/iOS`에 있는 공통 Apple 실행 코드도 iOS·macOS 빌드에서 함께 사용한다. 프레임워크는 각 플랫폼의 SDK로 빌드한다.

앱 target은 공용 framework에 링크하고 자원 bundle을 앱에 포함한다. 의존 관계와 번들 복사는 `Modules/project.yml`, `iOS/project.yml`, `macOS/project.yml` 및 생성된 프로젝트에서 확인한다. [Apple: target 의존 관계](https://help.apple.com/xcode/mac/current/en.lproj/devcc9f6bfb2.html).

**효과와 검증 범위**

이 구성에서는 게임 규칙을 한곳에서 수정하고 세 플랫폼에 적용할 수 있다. 공용 코드 변경의 영향도 세 플랫폼에서 검사해야 한다. Mac 개발 중에는 표시 대기·표면 갱신·Retina 설정과 서명 문제를 수정했다. 해당 원인과 계측 결과는 트러블슈팅에 정리한다.

workspace 파일과 세 project 명세에 의존 관계를 기록했다. 플랫폼별 일반·치트 빌드에서 입력·무기·자원을 검사했다. Android는 같은 C++ 소스를 NDK/CMake로 빌드하고 OS 연결부를 추가할 계획이다.
