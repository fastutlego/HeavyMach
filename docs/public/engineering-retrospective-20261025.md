# HeavyMach 복원·버그 수정 기록

2026년 10월 25일 기준 · 제품 코드 기준 `72e8c68e` · 공개용 기술 회고

## 현재 앱과 복원 과정

Codex는 HeavyMach 1.13을 현재 아이폰에서 실행할 수 있는 C++·Objective-C++ 소스로 복원했다. 렌더링, 음향, 시간 진행, 저장, 입력에서 정상 IPA 호환 실행판과 달랐던 부분을 고쳤다. 이후 나는 넓은 게임 화면, 자동 일시정지, 검증용 조작 버튼과 메뉴 배경 확장을 요구했고 Codex가 구현했다.

2026년 10월 25일 제품 코드 `72e8c68e`의 일반 앱과 치트 앱을 같은 아이폰에 설치하고 각각 타이틀을 확인했다. 일반 앱에는 치트 버튼이 없고 설치 직후 저장 파일은 설치 전 백업과 같았다. 현재 설치본의 모든 미션을 직접 플레이했고 크래시·오동작·적 이동 이상은 보이지 않았다.

두 판본을 실제 폰에서 잠깐 실행해 보니 동작에 차이가 있었다. 호환판에는 없던 프레임 저하가 복원판에 있었다. 나는 정상판과 코드를 비교하고, Xcode 도구로 병목을 측정하고, 원본 규칙을 맞추라고 지시했다.

아래 계측값은 각 수정 당시의 검사다. 내 직접 플레이와 Codex의 자동 검사 결과는 따로 기록했다. 전체 화면 단일 문, 물리 회전과 장시간 발열 검사는 남아 있다. 여기서 일반 앱은 개발 서명으로 설치한 게임 앱, 치트 앱은 별도 저장과 조건 설정을 갖춘 검증 앱이다.

## 비교 대상

비교 대상은 세 가지였다.

| 대상 | 확보한 것 | 비교에 쓰는 역할 |
|---|---|---|
| 원본 IPA | 배포 실행파일과 게임 자원 | 원본 함수·데이터·자원 이름·호출 순서 확인 |
| 정상 IPA 호환 실행판 | 원본 ARM 코드를 실행하고 그래픽·음향 호출을 호스트에 연결하는 실행 환경 | 내가 정상 동작을 확인한 행동 기준 |
| 소스 복원판 | C++와 Objective-C++로 복원한 게임·iOS 연결 코드 | 수정·빌드·계측할 제품 |

IPA에서 실행 코드·자원·OpenGL 호출을 확인했다. 원 개발자의 프로젝트 소스는 제공되지 않아 실행파일 분석과 원본 실행 관측으로 동작을 복원했다.

정상 실행판과 입력·상태를 맞추면 복원 과정에서 생긴 차이를 좁힐 수 있다. Codex가 내 지시에 따라 렌더·음향·타이머·저장·입력을 대조했다. 이후 승인된 넓은 시야, 양방향 가로 대응, 자동 일시정지, 치트 입력은 추가 요구로 관리하고 원본 480 비교 모드를 유지했다.

## 1. 렌더링·음향 구현 오류

초기 복원판은 UIKit 이미지 합성과 CPU 래스터를 사용했다. 이후에는 스프라이트마다 픽셀 연산, 행 뒤집기, 복사, 이미지 객체 생성과 합성이 반복되는 경로도 있었다. 정상판이 사용한 GLES 경로와 달리 CPU 작업을 늘렸고, 성능과 동작을 먼저 비교하지 않은 선택이었다.

기존 UIKit 검사에서 슬롯 미리보기의 평균 draw는20.187ms, 사격은19.506ms였다. 각120개 표본 모두16.67ms를 넘었다. 오디오를 제외한 검사였으므로 음향만 수정해서 해결할 수 있는 문제도 아니었다. 측정 대상은 오프스크린 draw 처리시간이었다.

제품 경로를 OpenGL ES1.1로 바꾸고 텍스처 업로드 후 CPU 픽셀을 해제했다. 공유·화면·월드 자원을 분리하고, 이미 준비한 자원을 매 프레임 다시 해석하지 않도록 했다. CPU 렌더와 이미지 readback은 비교 검사에 남겼다.

렌더를 바꾼 뒤에도 사격 지연이 남았다. 분리 계측에서 AVAudioPlayer 재시작 호출은 평균52.887ms, p95 58.549ms였다. 호환판의 OpenAL Soft1.22.2와31개 원본 음원을 재사용하고 buffer/source를 미리 준비하자 해당 호출 평균은0.007053ms, p95는0.008167ms가 됐다. 두 수치는 같은 종류의 오디오 호출 비용을 비교한 값이다.

음향은 호환판의 구현 소스를 재사용했다. 그래픽은 원본 GLES 호출과 상태 규칙을 바탕으로 다시 구현했다.

## 2. 시간 계산·저장 오류

시간 누적기로 늦어진 시간을 따라잡는 방식은 다른 게임에서 유효할 수 있다. 그러나 이 원작은 프레임마다 정해진 시간을 한 번 더하는 동작이었다. 복원판의 누적 계산은 한 표시 프레임에서 게임을0회 또는2회 진행시킬 수 있었다. 내 지적 이후 한 프레임 한 tick으로 맞추고, 호환판의 다음 기한 계산을 일회용 NSTimer에 연결했다. 비활성 중 지난 시간을 복귀 때 몰아서 진행하지 않는다.

약32~33ms 간격을 설명할 때도 서로 다른 현상을 혼동하지 않아야 했다. 타이머 예약 차이, 화면 처리시간, 최종 제출 지연은 별개의 측정 대상이다. 후속 시뮬레이터 검사에서는 최종 확대·제출이 비용을 지배했고, 정상 포팅판도 같은 환경에서 약49회/초 수준이었다. 이 실행에서는 두 판본 모두 Simulator의60Hz 기준에 실패했다.

저장에서는 탄약·피격·경험치의 메모리 변경 통지를 실제 파일 쓰기에 연결한 접근이 잘못이었다. 원본의 네 저장 지점인 슬롯 선택, 다음 스테이지, 게임오버, 메뉴 복귀만 파일 쓰기로 연결했다. 실제 임시 파일 검사에서180프레임 사격 중 추가 쓰기0회, 메뉴 복귀1회, 단순 백그라운드 진입0회를 확인했다.

저장 형식3624바이트와 미확인 바이트도 보존했다. 현재 C++ 구조체를 그대로 저장하지 않고 원본 오프셋과 바이트 연산을 사용한다. 이벤트를 나중에 처리하면서 다른 시점의 슬롯을 저장하지 않도록 이벤트 발생 시점의 상태도 고정했다.

## 3. 시뮬레이터·아이폰 성능 측정

Codex는 시뮬레이터에서 CPU 병목, 자원 재사용, 메모리, 입력 변환과 화면 범위를 검사했다. 실제 아이폰의 프레임과 열 상태는 기기를 연결한 뒤 따로 측정했다.

실제로 Time Profiler, Allocations/Leaks, Metal System Trace를 수집했다. 한 기록의 앱 CPU 샘플에서 화면 표시 함수를 포함한 비율은70.97%, 게임 tick은0.31%였다. 짧은 메모리 기록에서는127.62MiB의 Heap+Anonymous VM과 누적 할당1.76GiB를 관측했고 Leaks 검출은0건이었다. 1.76GiB는 검사 중 할당을 합친 값이다. 현재 사용량은 127.62MiB였으며 장시간 누수 검사는 남았다.

Metal trace에 호스트 GPU 이벤트가 잡혀도 앱의 OpenGL GPU 시간·카운터가 분리되어 수집된 것은 아니었다. 당시 GL_RENDERER는 Apple Software Renderer였다. 이 환경은 Mac의 소프트웨어 렌더 경로였으므로 실제 아이폰 성능은 별도 기기 기록으로 판단했다.

실제 아이폰에서는 별도로127.77초의 Game Performance 기록을 얻었다. 주 화면 갱신은59.71회/초, 간격 p95는16.67ms, 최대50.02ms였다. 대부분 정지한 탱크의 전투 구간이었고 열 상태는 기록 내내Serious였다. 수정 뒤 직접 플레이했을 때 프레임 저하는 느껴지지 않았다. 연속 이동·사격과 정상 초기 열 상태의 장시간 비교는 후속 검사로 남았다.

## 4. 조작·효과음·일시정지 수정

원격 화면 조작만으로 실제 폰을 기울이기는 어렵다. 치트 앱의 좌우·정지 버튼은 이 제약을 해결하기 위한 검증 수단이었다. 같은 게임 입력 경로를 거치도록 구성하고 일반 앱에는 포함하지 않았다. 실제 폰에서 버튼으로 이동·점프·사격·무기 전환을 관측했다. 폰을 기울이는 센서 검사는 별도 항목이다.

틸트 반전은 별도의 구현 오류였다. 원본 포팅판의 고정 가로 방향을 이유로 방향 보정을 제거하면서, 새 앱이 양방향 가로를 허용한다는 조건을 놓쳤다. 현재 UI 방향에 맞춰 센서 X/Y를 정규화한 뒤 원본50Hz 필터에 넣도록 복구했다. 이미 화면 기준인 치트 버튼 입력에는 두 번 반전하지 않는다. 수정 전 LandscapeRight의 좌·우 이동 단언이 실패했고 수정 후 관련4개 검사가 통과했다.

무기 전환음은 음원 파일 부재가 아니라 버튼 release 경로의 효과음4 호출 누락이었다. 원본 호출을 복원했다. 효과음 호출과 오디오 엔진 동작을 검사했다. 스피커 청취 검사는 당시 후속 과제로 남았다.

백그라운드·잠금과120초 무입력 정지는 내가 승인한 새 사용성 정책이다. 원본 delegate에는 이 처리가 없어 새로 추가했다. 비활성 진입에서 게임·입력·음향·타이머·센서를 정지하고 복귀 후 명시적인 재개를 요구한다. 결과·업그레이드 상태를 유지하며 시간 보충과 추가 저장을 만들지 않는다. Codex가 실행한 관련 iOS21개와 코어17개 검사가 통과했고, 실제 폰의 홈 이동→복귀→정지 유지→재개도 관측됐다. 실제 잠금 버튼 경로, 스피커 청취, 물리180도 회전은 별도 범위로 남았다.

## 5. 화면 확장 후 발생한 오류

나는 좌우 잘림을 해결할 때 그림을 크게 늘이기보다 더 넓은 월드를 보여주자고 제안했다. 원본 오브젝트 크기를 지키는 관점에서 타당했다. Codex는 논리 높이를320으로 유지하고 폭을 기기 비율에 따라 늘렸다. 논리 높이320의 게임 화면을 기기의 실제 픽셀 크기로 확대한다.

월드, HUD, 결과 일러스트, UIKit 터치를 각각 구분해야 했다. HUD는 안전영역 안에 두고, 입력은 실제 표시 변환의 역변환을 사용했다. 나는 확장 가장자리에서도 사격을 확인하라고 요구했다. Codex는 실제 폰에서 입력·조준·탄환을 대조했다. 왼쪽 추가 영역도 입력을 받았지만 탱크 후방일 때 원작 전방 사격 조건에 따라 발사하지 않는 경우가 있었다. 입력 불능과 게임 규칙에 따른 비발사를 구분했다.

클리어 그림 문제는 두 차례 다른 원인으로 나타났다. 처음에는 로더가 원본 JPEG를 읽는데 HUD가 옛 변환 파일명처럼 `.png`를 덧붙여 그림이 누락됐다. 원본 이름으로 복구한 뒤 내가 실제 표시를 확인했다. 이후 전체 화면 확장에서는 일러스트에도 중앙480 HUD의 clip을 적용해 바깥 월드가 노출됐다. 그림은 전체 화면을 비율 유지 cover로 덮고, 글자·버튼은 기존 HUD 변환으로 되돌리는 방식으로 수정했다. 결과15종×3크기의45조합을 검사했다.

필살기 후방 낙하는 원본 분산 수식이 아니라 해제 이벤트의 가짜 좌표가 원인이었다. 해제 때 전달한 `(0,0)` 또는 화면 밖 고정 좌표가 남은 연사의 목표점을 바꿨다. 정상 해제에는 실제 좌표를 보내고 취소·정지에는 발사 상태만 끄도록 분리했다. 포탄·미사일·하늘 레이저를 포함한20무기×3크기×6입력, 총360조건과1,080발을 실제 폰에서 검사했다. 무기별 전체 연사·목표·탄약을 확인했으며 데미지·중력·원본 분산식은 유지했다.

보스 이동은 또 다른 영향이었다. 시야를 넓히며 보스를 일찍 생성했는데 이동·무기 AI도 함께 실행했다. 미션3-5 항공기는 접근 전30초 비교에서 최대472.646단위 먼저 왼쪽으로 이동했다. 표시 준비와 전투 활성을 분리하자 접근 전 이동은0이 됐다. 원작의 접근500단위·진행10단위 조건과 전투 경계는 유지했다.

처음에 비행 이동 타입을 헬기형으로 설명한 것도 잘못이었다. 내 외형 정정 후 스테이지·모델·부품 연결을 확인했다. 다른 적의 고정 좌표·활성 조건과 화면 확장의 간섭은 후속 조사 항목으로 남았다. 원본 속도·거리·사거리 전체에 화면 폭 비율을 곱하면 난이도까지 달라지므로 일괄 보정하지 않았다.

## 6. 메뉴 배경·검은줄 수정

온보딩·메뉴는 월드와 달리 한 장의 배경에 장식과 글자가 포함된 경우가 있었다. 버튼·문구는 원본 비율을 유지해 재배치하고, 배경은 원본 옆에 별도 그림을 붙이는 방식을 채택했다. 슬롯 카드의 표시와 터치 영역에는 같은 이동량을 적용했다.

imagegen으로 만든 넓은 그림은 중앙까지 원본으로 채택하지 않았다. 생성 결과의 좌우만 사용하고 중앙은 원본 파일을 그렸다. 원본 이미지695개는 IPA와 SHA256이 같음을 확인했다. 생성 파일, 프롬프트, 참조와 채택 이유는 따로 관리했다.

처음 모드·미션에 공통 금속 배경을 넣은 접근은 빈 공간을 채웠지만 원본과 연결된 화면이라는 요구를 충족하지 못했다. 내 지적 후 각 원본의 철판·레일 높이, 밝기, 질감을 기준으로 별도 좌우 배경을 만들었다. 실제 합성 화면과 선택 동작을 다시 검사했다.

타이틀 양쪽 검은줄은 생성 그림만의 문제가 아니었다. 확대·회전과 비정수 위치에서 필터가 텍스처의 검정 여백을 읽었다. 흰 배경 대조 검사도 가장자리 밝기가153~204로 떨어졌고, 배경 경계 반 texel의 UV를 유효한 색에 고정한 후 세 조건 모두255를 유지했다. 중앙 UV와 원본480/sprite 경로는 유지했다. Codex가 실행한 최종 시뮬레이터·실제 아이폰 검사 각각26개가 통과했고, 이어 타이틀·모드·미션 화면도 확인했다.

문 전환은 아직 남은 문제다. 초기 확장 구현은 원본 셔터를 중앙·좌·우에 반복해 화면 교체를 가렸다. 가림 자체는 했지만 좌우에도 별도 문이 움직이는 모양이 됐다. 나는 화면 전체를 덮는 하나의 문 구조로 바꾸는 방향을 승인했다. 중앙 장식과 원작 상하·좌우 문짝 순서·음향·완전 닫힘 시 교체는 유지하고 바깥 철판을 확장하는 계획이다. 단일 문은 구현과 시뮬레이터 검증이 남아 있다.

## 7. 빌드·기기 연결 문제

CLI의 서명 오류, Xcode GUI의 서명 빌드, 앱 설치, 폰 잠금, 화면 조작 도구의 인증 오류는 서로 다른 단계였다. “빌드가 안 된다” 또는 “폰을 조작할 수 없다”로 묶어 설명하면 성공한 경로와 다음 조치를 놓친다.

CLI 서명 실패가 있어도 GUI 빌드가 성공한 앱은 서명·기기 프로파일·실행파일을 확인해 설치할 수 있었다. 잠긴 폰에는 설치가 성공하고 실행만 거부되는 경우도 있었다. 기기 잠금 해제 후 실행·검사를 계속했고 설치와 실행을 별도로 기록했다.

화면 조작 연결에서는 앱을 재시작해도 별도의 영속 서버가 이전 버전으로 남아 있었다. 공식 CLI로 서버를 갱신한 뒤 앱 목록, Xcode 창, Device Hub, 실제 아이폰 터치까지 순서대로 복구를 확인했다. “지원되는 갱신 경로가 없다”는 앞선 판단은 불완전했다. 확인한 복구 절차와 버전 확인 방법을 스킬로 남겼다.

| 필살기/무기 자동 검사 | 20종·360조건·1,080발의 목표/연사/탄약 검사 | 모든 무기의 모든 충돌·피해·수동 UI 순환·청취 완료 |
| 결과 화면 | 15개×3크기 표시·가림·버튼 검사 | 모든 장면의 내 미감 확인 |
| 항공기 보스 | 원작 접근 전 선행 이동·공격 제거 | 전체 적 AI와 확장 시야의 동등성 |
| 최종 배경·검은줄 | Simulator26/26, 실제 Air26/26, 직접 메뉴 조작 | 물리 Pro Max·OS 회전·장시간 GPU 성능 검사 |

표는 서로 다른 시점의 검사 결과를 담고 있으며 일부 사례가 겹친다. 전체 iOS 검사에서 표시시간16.67ms 기준 실패가 남았다. 이후 메뉴 검사는 통과했다. 각 실행의 조건과 로그는 연결된 기록에 있다.

사진 비교에서 채널 차이1을 허용한 검사는 기존 GL 기준과 같은 계약을 적용한 것이다. 같은 직접 렌더를 반복해도 최대1 차이가 관측됐고 DITHER를 꺼도 남았다. 완전 일치가 실패했다는 사실을 기록하고, 화면 전체 가림은 별도 단색 exact 검사로 확인했다. 원본 파일 불변은 SHA로 따로 검사했다.

## 9. 현재 남은 과제

1. 전체 화면을 덮는 단일 문 구조와 모든 메뉴·전투 전환의 시뮬레이터 검증.
2. 모든 적 계열·보스·Survival의 고정값과 확장 시야 간섭 예방 감사. 직접 한 전체 미션 플레이에서는 적 이동 이상이 관측되지 않았다.
3. 실제 OS180도 회전, 센서 틸트, HUD·터치·중단 상태를 함께 다루는 검사.
4. 같은 초기 열 상태에서 비교판과 복원판의 장시간 반복3회 계측과 발열 대책 검증.
5. 첫 실행 전체 경로와 업그레이드 등 나머지 화면의 전체 화면 디자인 검수.
6. 전체 무기의 수동 전환·시각 효과·출력음과 모든 충돌/피해 조합 확인.
7. 접히는 기기의 자세 감지와 화면/조작부 분할 UI 검토·구현.
8. 모든 원본 함수와 전체 캠페인 상황의 동등성 확인.

## 10. 후속 작업 규칙

정상 실행판이 있으면 먼저 같은 입력·상태로 비교한다. 원본과 다른 설계를 넣을 때는 필요성과 영향을 기록한다. 원작 복원과 내가 승인한 개선을 구분한다.

좌표는 월드·카메라·HUD·터치로 나누고 같은 표시 변환의 역변환을 입력에 사용한다. 자원은 준비·재사용·해제를 명시한다. 메모리 상태 변경과 파일 쓰기를 분리한다. 데미지·경험치·탄약은 원본 데이터와 정수 절삭·연산 순서까지 보존한다. 예를 들어 데미지 `D+(D/8)*G`의 정수 나눗셈을 다른 대수식으로 바꾸지 않는다.

빌드, 서명, 설치, 실행, 직접 조작, 자동 검사, 장시간 성능을 각각 보고한다. 도구의 제약은 정확한 실패 단계와 가능한 대안으로 설명한다. “콜백” 같은 구현 용어만으로 지연을 설명하지 않고, 무엇이 호출됐으며 어디서 얼마나 기다렸는지를 제시한다. 기능 검사를 내게 반복해서 떠넘기지 않되 물리 회전·청취처럼 직접 수행하지 않은 범위는 밝힌다.

후속 수정도 내 지시와 원본 동작을 따른다. 관련 정책·코드·검사를 함께 바꾸고 실행 결과를 현재 상태 문서에 반영한다.
