# HeavyMach IPA 포팅과 네이티브 앱 복원

2026년 10월 26일 작성 · 앱 기준 `72e8c68e`

Codex는 HeavyMach 1.13의 IPA를 현재 아이폰에서 실행한 뒤, 게임 코드를 수정하고 빌드할 수 있는 별도 앱을 만들었다. 처음에는 새 앱에서만 프레임 저하가 나타났다. 정상 동작하던 IPA 호환판과 비교하면서 렌더링, 음향, 시간 계산, 저장 방식을 고쳤다. 마지막에는 같은 게임 코드를 사용하는 치트 앱과 일반 앱을 아이폰에 설치했다. 나는 설치본의 모든 미션을 플레이했고 크래시·오동작·적 이동 이상은 보이지 않았다.

두 앱을 만드는 방법은 달랐다. IPA 포팅판은 원본 ARMv6 실행파일을 호환 실행기로 구동했다. 새 앱은 분석한 게임 규칙을 C++로 구현하고, 창·입력·화면·음향을 Objective-C++로 연결했다. 새 앱의 실제 구현 언어는 C++·Objective-C++이며 Swift는 사용하지 않았다.

## 1. 원본 IPA 실행

처음 확보한 것은 개발 프로젝트가 아니라 배포된 IPA였다. 그 안에는 ARMv6 실행파일과 이미지, 음원, 맵, 무기·기체 데이터가 있었다. 실행파일에서 게임 규칙을 분석할 수는 있었지만, 원 개발자의 프로젝트를 그대로 열어 다시 빌드할 수 있는 상태는 아니었다.

우선 원본 게임을 실행했다. touchHLE 계열의 Rust CPU 인터프리터가 포함된 기존 iOS 포트를 기반으로 HeavyMach용 실행 환경을 구성했다. 이 경로는 JIT를 사용하지 않는다. 원본 ARM 명령을 인터프리터로 실행하고, 원본이 호출하는 iOS·그래픽·음향 기능을 호스트에서 처리한다. 게임의 이동이나 데미지 계산은 원본 실행파일이 담당한다.

가져온 실행기에는 다른 게임을 위한 코드가 섞여 있었다. HeavyMach 진입점을 추가하고 MoleWorld 전용 후킹을 비활성화했다. CPU 코드의 특정 게임 주소 우회도 제거하고 일반 실행 경로의 회귀 검사를 통과시켰다. Rust와 SDL 바인딩의 버전·커밋을 고정하고, Xcode가 Rust 실행기를 빌드한 다음 원본 앱 자원을 패키징하도록 구성했다. 원본 IPA의 해시를 검사해 다른 파일이 들어가면 패키징 단계에서 멈추게 했다.

시뮬레이터와 아이폰용 빌드는 성공했지만, 실제 폰에서는 앱이 처음부터 정상 실행되지는 않았다. 초기 실행은 UIScene 미채택 오류로 종료됐다. SDL의 iOS 연결 코드에 scene과 window 연결, 전경·배경 이벤트 처리를 추가했다. 전역 방향 값이 Unknown인데 실제 scene은 Landscape인 경우도 있어 화면 크기를 계산할 때 scene의 방향을 먼저 사용하도록 바꿨다.

서명에서도 별도 문제가 있었다. 패키징한 실행파일의 오래된 수정 시각 때문에 Xcode 증분 빌드가 서명 단계를 건너뛰었고, 설치할 때 `No code signature found`가 발생했다. 패키징 직후 실행파일 시각을 갱신하고 Clean Build로 다시 서명했다. 이후 설치와 실행을 확인했다.

시뮬레이터에서는 키보드 방향키를 기울기 입력으로 변환했다. 키를 놓으면 중립으로 돌아가게 했다. 실제 아이폰은 원래 기울기 센서를 사용했다. Codex는 메뉴 진입·사격·일시정지를 확인했다. 나는 미션 전환, 낙사 처리, 아이템 획득, 새 무기 사용과 재실행 후 저장 유지를 확인했다. 이 실행본을 이후 비교 대상으로 보존했다.

## 2. 게임 코드 복원

다음 목표는 게임 규칙을 수정할 수 있는 소스를 만드는 것이었다. 호환판에서는 원본 ARM 코드가 게임을 실행하므로, 실행 성공만으로 편집 가능한 게임 소스를 얻은 것은 아니었다.

REA와 Ghidra로 원작 함수의 의사 코드와 어셈블리를 추출했다. Objective-C 메타데이터에서는 클래스·메서드·필드와 주소를 확인했다. 디컴파일 결과의 인수나 자료형이 어색하면 실제 ARM 호출 레지스터와 호출부를 대조했다. 구조체 인수를 작은 실수로 잘못 표시한 결과를 그대로 C++ 조건식에 옮기지 않기 위해서였다.

데이터도 함께 복원했다. 원작의 WeaponInfo 160개, PartsInfo 294개, MachInfo 720개를 reader와 setter에 대조해 무기·부품·기체 구조를 만들었다. MAP/MCH는 중첩 노드의 헤더, payload와 자식 수를 순서대로 읽었다. 원본 이미지 695개와 WAV 31개는 계속 재사용했다.

구현은 게임 로직과 iOS 코드를 나눴다. C++의 `GameSession`, `World`, `Player`, `Enemy`, `Combat`이 이동·전투·진행을 처리하고, Objective-C++의 `HMGameView`가 입력과 표시를 연결했다. 저장 파일은 원본의 3,624바이트 형식을 유지했다. 현재 컴파일러의 구조체를 그대로 쓰지 않고 원본 필드 오프셋으로 읽고 기록했다.

계산식도 원본 연산 순서를 따랐다. 예를 들어 강화 데미지는 `D+(D/8)*G`이며 `D/8`은 정수 나눗셈이다. 이를 실수 계산으로 바꾸면 작은 데미지의 결과부터 달라진다. 이처럼 겉으로 비슷한 화면보다 실제 데이터와 경계값을 먼저 검사해야 하는 부분이 있었다.

분석 방법과 전체 함수 목록은 별도의 [REA 활용 내역](rea-restoration-method-20261025.md)에 정리했다.

## 3. 새 앱에서 발생한 프레임 저하

초기 새 앱은 UIKit 이미지 합성과 CPU 렌더링을 사용했다. 원본의 GLES 동작을 분석했어도, 실제 화면을 만드는 코드는 별도 방식으로 작성한 것이다. 스프라이트 픽셀 처리, 복사, 이미지 객체 생성과 합성이 반복됐다.

두 버전을 실제 아이폰에서 짧게 실행해 보니 차이가 있었다. IPA 호환판에는 프레임 저하가 없었는데 새 앱에는 있었다. 나는 정상판과 비교하라고 지시했고 Codex가 구현 차이를 대조했다. 처음부터 두 판본을 같은 조건으로 비교한 뒤 구현을 선택했어야 했다.

비교는 한 번의 전체 벤치마크로 끝나지 않았다. 먼저 렌더링과 사격 시 음향 비용을 분리했고, 그 뒤 시간 진행·예약 방식과 저장·자원 수명을 대조했다. 수정 후에도 남은 지연은 같은 시뮬레이터에서 타이틀과 빈 슬롯 메뉴를 각각 실행해 확인했다. 다음 절의 수치는 이 과정에서 남긴 서로 다른 실행 기록이다.

## 4. 렌더링·음향 비교

오디오를 제외한 초기 렌더 검사에서도 슬롯 미리보기 평균은 20.187ms, 사격은 19.506ms였다. 각 장면의 120개 표본이 모두 16.67ms를 넘었다. 사격할 때 끊긴다는 관측이 있었지만, 소리만 고쳐서는 해결되지 않는 상태였다.

게임 그래픽을 OpenGL ES 1.1 경로로 바꿨다. 원본의 텍스처 형식·UV·필터·블렌딩·그리기 순서를 복원하고 GPU에 올린 뒤에는 CPU의 디코딩 픽셀을 해제했다. 같은 이미지를 매 프레임 다시 해석하지 않도록 공유 자원과 화면·월드 전용 자원도 구분했다. UIKit은 창·입력·검증 패널을 담당하게 됐다.

그 뒤에도 사격 지연이 남았다. 음향 호출을 따로 측정하자 AVAudioPlayer 재시작이 한 실행에서 평균 52.887ms, p95 58.549ms를 차지했다. 게임 프레임 한 번의 예산보다 훨씬 긴 호출이었다.

호환판에서 사용하던 OpenAL Soft 1.22.2 소스를 재사용했다. 원본 WAV 31개의 buffer와 source를 미리 준비하고 사격 때 재사용했다. 이후 같은 종류의 호출 비용은 평균 0.007053ms, p95 0.008167ms였다. 그래픽은 원본 GLES 규칙을 구현한 새 코드였고, 음향은 호환판의 라이브러리 소스를 재사용했다.

## 5. 시간 계산·저장·자원 수명 비교

프레임 지연을 조사하면서 시간 진행 방식도 달랐다는 사실을 확인했다. 원작의 `renderScene`은 호출될 때마다 정해진 시간을 한 번 더했다. 새 앱은 실제 경과 시간을 누적한 뒤 필요한 만큼 게임을 갱신했다. 이 때문에 화면 한 번을 표시하는 동안 게임을 0회 또는 2회 갱신할 수 있었다.

실제 `HMGameView.frame`을 호출하는 검사에서 timestamp에 ±0.3ms 흔들림을 주자 수정 전에는 600회 중 599회가 원본의 한 번 갱신 기준과 달랐다. 누적 보충 계산을 제거한 뒤에는 같은 조건에서 불일치가 0회였다. 이후 예약 방식도 호환판의 다음 기한 계산과 비교해 일회용 NSTimer로 바꿨다. 비활성 상태에서 지난 시간을 복귀 후 몰아서 처리하지 않게 했다.

저장도 잘못 연결돼 있었다. 탄약이나 경험치가 메모리에서 바뀌었다는 통지를 실제 파일 쓰기로 처리했다. 원본 호출부를 확인해 슬롯 선택, 다음 스테이지, 게임오버, 메뉴 복귀의 네 지점에서만 저장하도록 수정했다. 임시 파일을 사용한 검사에서 180프레임 사격 중 추가 쓰기는 0회, 메뉴 복귀는 1회였다.

자원 해제 시점은 원본 함수와 소유자를 대조했다. 이전 화면의 전용 텍스처와 맵 자원을 해당 화면에서 나갈 때 해제했다. 맵과 메뉴를 여섯 번 오간 검사에서 전용 텍스처 수가 누적 증가하지 않았고, 업로드한 이미지의 CPU 픽셀도 남지 않았다.

이 수정 뒤에도 시뮬레이터의 16.67ms 표시시간 검사는 실패했다. 최종 확대 패스와 화면 제출을 따로 계측하자 Apple Software Renderer의 처리 비용이 대부분을 차지했다. 같은 환경에서 호환판의 빈 슬롯 메뉴는 평균 48.670회/초, 새 앱은 50.159회/초였다. 둘 다 실제 디스플레이의 주사율이 아닌 호출·표시 계수이며, 시간과 난수까지 동기화한 비교는 아니었다. 다만 이 메뉴에서 새 앱이 호환판보다 느려지는 현상은 관측되지 않았다.

실제 아이폰에서는 별도로 127.77초를 기록했다. 주 화면 갱신은 59.71회/초, 간격 p95는 16.67ms였다. 수정 뒤 직접 플레이했을 때 프레임 저하는 느껴지지 않았다. 당시 열 상태는 Serious였으므로 장시간 발열 비교는 후속 과제로 남겼다.

## 6. 치트 앱과 일반 앱 분리

복원 과정에서는 특정 미션, 무기, 부품 조건을 반복해서 만들 필요가 있었다. 원격 조작으로 실제 폰을 기울이기도 어려웠다. 검사를 위해 매번 처음부터 진행하는 대신 별도 치트 앱을 만들었다.

Xcode target을 `HeavyMachValidation`과 `HeavyMachRestored`로 나눴다. 두 target은 같은 게임 코어를 빌드하며 `HM_VALIDATION` 조건으로 검증 패널과 방향 버튼을 구분한다. bundle identifier와 저장 공간도 분리해 일반 앱의 진행 데이터를 치트 설정이 덮지 않도록 했다.

치트 앱에서는 미션·시작 위치·EXP·무기·부품을 설정하고 좌우 이동·정지 버튼을 사용할 수 있다. 설정 후 실제 이동·사격·성장·저장은 공통 게임 코드가 처리한다. 따라서 치트 패널의 값만 확인하지 않고, 입력 후 실제 탱크 위치와 생성된 탄환·소비한 탄약을 검사했다.

일반 앱에서는 검증 버튼 없이 원래 게임 조작과 진행을 제공했다. 내가 부른 “정식 빌드”는 이 일반 앱이며, 이 작업의 배포는 개발 서명으로 아이폰에 설치한 단계다.

## 7. 전체 화면 지원 후 추가 수정

Codex는 성능과 원본 동작을 수정한 뒤 내가 요청한 전체 화면 지원을 구현했다. 논리 높이는 320으로 두고 기기의 가로세로 비율에 맞춰 폭을 늘렸다. 탱크와 지형을 크게 늘이는 대신 더 넓은 월드를 표시했다. HUD는 안전영역에 배치하고 터치는 화면 표시 변환의 역변환으로 월드 좌표를 구했다.

이 변경은 그리기 범위만 넓히는 것으로 끝나지 않았다. 필살기를 사용한 뒤 손을 떼면 일부 탄환이 탱크 뒤로 떨어졌다. 원인은 원본 분산식이 아니라 해제 이벤트에 보낸 가짜 좌표였다. 남은 연사가 `(0,0)` 또는 화면 밖 고정 좌표를 새 목표점으로 사용했다. 정상 해제에는 실제 좌표를 전달하고, 취소·정지에서는 발사 상태만 끄도록 나눴다. 이후 포탄·미사일·하늘 레이저를 포함해 20종 무기, 360조건, 1,080발의 목표·연사·탄약을 아이폰에서 검사했다.

미션 3-5 항공기 보스는 넓어진 시야에서 미리 생성되면서 이동과 공격도 먼저 시작했다. 접근 전 30초 비교에서 최대 472.646단위 먼저 왼쪽으로 이동했다. 표시 준비와 전투 활성을 분리하자 접근 전 이동은 0이 됐다. 속도나 사거리를 화면 폭에 비례해 늘리는 방식으로 보정하지는 않았다.

결과 일러스트에는 두 오류가 있었다. 먼저 원본 JPEG 이름에 옛 변환 파일의 `.png` 접미사가 남아 그림을 못 찾았다. 이를 고친 뒤 내가 표시를 확인했다. 화면 확장 후에는 중앙 HUD의 clip 때문에 그림 바깥으로 월드가 보였다. 일러스트는 비율을 유지한 채 전체 화면을 덮고 글자·버튼만 기존 HUD 배치를 사용하도록 수정했다. 결과 그림 15개를 크기 3종에서 검사했다.

메뉴는 원본 중앙 그림을 유지하고 좌우에 별도 배경을 추가했다. 모드·미션 배경은 각 원본의 철판·레일에 맞춰 다시 제작했다. 타이틀의 검은줄은 확대·회전 때 텍스처의 검정 여백을 읽는 문제였다. 배경 경계 UV를 수정한 뒤 Simulator와 실제 iPhone Air에서 각각 26개 검사를 통과했다.

## 8. 설치와 전체 미션 확인

최종 제품 코드 `72e8c68e`의 치트 앱과 일반 앱을 같은 아이폰에 설치하고 각각 타이틀 화면을 확인했다. 일반 앱에는 검증 버튼이 없었고, 설치 직후 저장 파일은 설치 전 백업과 같았다. 앞선 치트 앱 검사에서는 이동·점프·사격·무기 전환과 메뉴 조작을 직접 확인했다.

이후 설치본의 모든 미션을 직접 플레이했을 때 크래시·오동작·적 이동 이상은 보이지 않았다. 원본 IPA 실행, 편집 가능한 게임 코드 복원, 치트·일반 앱 구성, 실제 폰 설치와 캠페인 플레이 확인까지 진행한 결과다.

남은 작업도 있다. 전체 화면 단일 문 전환은 구현 전이며, 물리 180도 회전·틸트 통합 검사, 장시간 발열 비교, 나머지 메뉴의 전체 화면 검수와 모든 무기의 충돌·피해·청취 검사는 추가로 해야 한다. 현재 완료 범위는 아이폰에서 플레이 가능한 복원 앱과 두 빌드의 설치·직접 한 전체 미션 확인이다.
