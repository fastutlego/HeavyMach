# HeavyMach 트러블슈팅

사용자는 직접 플레이한 결과를 기준으로 원작과 다른 움직임·사격·그림·성능을 지적했다. Codex가 만든 코드에서 차이를 찾고, 해당 경로를 수정한 뒤 같은 조건으로 검사했다. 아래는 기능 구현 중 발생한 17개 문제와 수정 결과다.

## 1. 사격·피격 때마다 파일 저장

사용자는 “발사 때마다 파일을 저장?”이라고 물었다. 초기 코드는 탄약·피격·경험치의 메모리 변경 통지 `changed()`를 파일 저장에 연결했다. 전투가 계속되는 동안 작은 상태 변화가 매번 디스크 쓰기로 이어졌다.

문제는 게임 상태 갱신과 영구 저장의 결합이었다. 메모리 값은 즉시 갱신하되 파일 쓰기는 슬롯 선택·다음 스테이지·게임 오버·메뉴 복귀 네 시점으로 분리했다. 저장 형식 3,624바이트는 유지했다.

180프레임 사격 검사에서 파일 쓰기 0회, 메뉴 복귀에서 1회, 백그라운드 전환에서 0회를 확인했다. 이후 키보드 입력과 항공기 추가에도 같은 원칙을 적용했다. [실행 정책](../runtime-policy.md), [저장 검사](../../Tests/iOS/HMSaveParityTests.mm)

## 2. UIKit에서 게임 그림을 매 프레임 생성

사용자는 정상 동작한 기준에서는 프레임 드랍이 없었는데 새 앱에서 발생한다고 지적했다. “UIKit으로 게임 그래픽 렌더링 하는 것 자체”의 타당성을 물었고, 기존 그래픽 경로와 비교하도록 지시했다.

초기 렌더링에는 CPU 픽셀 연산·행 뒤집기·메모리 복사·이미지 객체 생성과 합성이 있었다. 스프라이트를 GPU에서 그릴 수 있는 장면을 CPU에서 반복 처리했다. 오프스크린 120표본에서 슬롯 메뉴 20.187ms, 사격 19.506ms로 16.67ms를 넘었다.

OpenGL ES 1.1 경로를 복원하고 텍스처를 재사용했다. 업로드 뒤 필요 없는 CPU 픽셀 메모리를 해제했다. 이 변경 뒤에도 표시·음향·타이머 비용을 따로 검사했다. 사용자는 후속 iPhone 플레이에서 프레임 드랍이 보이지 않는다고 확인했다. [렌더링 정책](../rendering-policy.md), [이행 기록](../opengl-migration-20261024.md)

## 3. 사격 효과음 재시작 지연

렌더링 변경만으로 사격 지연을 설명할 수 없었다. 효과음을 `AVAudioPlayer`로 재시작하는 호출을 재니 평균 52.887ms, p95 58.549ms가 나왔다.

OpenAL 버퍼·소스를 미리 만들고 발사 때 재사용하도록 바꿨다. OpenAL 재생 호출은 평균 0.007053ms, p95 0.008167ms였다. 두 값은 음향 호출 비용이며 전체 게임 프레임 시간과는 별도다. [음향 계약·실행 정책](../runtime-policy.md), [OpenAL 검사](../../Tests/iOS/HMOpenALAudioTests.mm)

## 4. 시간 누적 계산으로 달라진 진행

사용자는 시간 누적 로직을 왜 넣었는지 물었다. 초기 구현은 실제 경과 시간을 누적하고 필요한 횟수만큼 게임 tick을 실행했다. 한 표시 호출에서 게임이 0회 또는 2회 진행되면서 원래의 이동·사격 감각과 달라질 수 있었다.

표시 호출마다 게임을 한 번 갱신하도록 맞추고 타이머 마감 시각을 조정했다. 일시정지·복귀 때 누적된 시간을 따라잡는 처리를 없앴다. 이동·무기·시간 검사는 이 규칙을 기준으로 실행한다. [실행 정책](../runtime-policy.md)

## 5. 약 32ms 지연을 하나의 원인으로 설명

사용자는 캔버스·좌표·화면 제출 등 기준과 다르게 구현한 부분을 비교하라고 요구했다. 타이머 간격, 게임 처리 시간, 화면 제출 대기를 섞어 설명하면 실제로 고칠 위치가 드러나지 않았다.

Instruments와 프레임 계측을 연결해 호출 간격·CPU 처리·표시 경로를 분리했다. Mac에서는 `flushBuffer`와 표면 갱신, iPad Simulator에서는 소프트웨어 픽셀 채우기가 큰 비용을 차지했다. Mac 수정 결과와 Simulator·실기기의 남은 기준 실패는 [검증 표](validation.md)에 각각 기록했다.

## 6. 틸트 반전과 가로 화면 회전

일반 앱 설치 후 사용자는 틸트 방향이 뒤집혔다고 지적했다. 센서 축, 기기의 가로 방향, 게임 이동 축을 연결하는 부분을 고쳤다. 이후에는 왼쪽·오른쪽 가로 회전에 맞춰 화면과 입력을 변환하도록 요구했다.

터치와 센서 변환을 좌표 정책에 묶고 두 가로 방향에서 사격·이동을 검사했다. 사용자는 화면 회전이 동작한다고 확인했다. 키보드는 같은 이동 경로에 가상 기울기를 전달하며 Shift로 작은 값을 만들 수 있다. [좌표 정책](../coordinate-policy.md), [입력 정책](../keyboard-input-policy.md)

## 7. 공중 지원 공격이 탱크 뒤로 낙하

사용자는 포탄·미사일·레이저 지원 공격 상당수가 터치한 곳보다 탱크 뒤로 떨어진다고 지적했다. 터치 해제 때 전달한 가짜 좌표가 낙하 지점 계산에 들어갔다.

해제 입력과 유효한 조준 좌표를 분리하고 마지막 공격 좌표를 유지했다. 사용자는 치트 앱에서 모든 무기를 검사하는 절차도 요구했다. 이후 무기별 선택·발사·충돌·해제 입력을 공통 검사에 넣었다. [수정 기록](../weapon-result-fix-20261025.md), [전체 무기 검사](../weapon-validation-procedure.md)

## 8. 미션 결과 일러스트 누락과 월드 노출

미션 클리어 뒤 그림이 나오지 않는다는 지적에서 자원 이름을 대조했다. JPG·PNG 접미사 대응이 잘못돼 결과 그림을 찾지 못하는 경로가 있었다. 이를 수정한 뒤 사용자가 실제 폰에서 그림을 확인했다.

넓은 화면에서는 결과 그림 밖으로 전장이 보였다. 결과 화면이 전체 캔버스를 덮도록 배경과 표시 영역을 고쳤다. 그림 로드와 화면 덮기를 별개로 검사했다. [그림 수정](../clear-illustration-fix-20261025.md), [결과 화면 수정](../weapon-result-fix-20261025.md)

## 9. 넓어진 화면에서 보스가 너무 일찍 접근

사용자는 미션3-5 항공기형 보스가 왼쪽으로 빨리 접근하고 오른쪽으로 잘 돌아가지 않는다고 했다. 처음에는 대상을 헬기로 잘못 식별했다. 사용자가 외형을 정정한 뒤 Stage14의 Boss05·E_Boss02를 대조했다.

화면 폭을 넓히자 기존의 가시성 판정과 전투 활성 조건이 더 일찍 충족될 수 있었다. 단순한 이동 속도 조절로 처리할 문제가 아니었다. 표시 범위와 보스 전투 활성 시점을 분리하고 해당 미션을 검사했다. 사용자는 이후 전체 미션 플레이에서 적 움직임 이상이 보이지 않는다고 확인했다. [보스 조사·수정](../boss-motion-fix-20261025.md)

## 10. 배경 연결·검은줄·도어 범위

메뉴 좌우에 추가한 그림이 중앙과 이어지지 않아 사용자가 수정을 요구했다. 연결부의 구조·명암·색을 맞춘 뒤 치트 앱에서 확인했다. 타이틀 경계의 검은줄은 텍스처 여백이 UV에 섞이는 경로를 수정했다.

기존 영역과 새 영역이 따로 열리고 닫히던 전환은 전체 화면을 덮는 도어로 바꿨다. 중앙 표식 크기를 유지하고 바깥 면을 늘리는 네 조각을 사용한다. HUD 클립을 해제하고 실제 캔버스에 맞춰 그린다. 닫힐 때 소수점 경계에서 틈이 생기지 않도록 표시 좌표를 정수화했다. 99tick 전환과 효과음 순서, 여러 화면 비율을 검사했다. [메뉴 경계](../menu-joins-20261025.md), [도어](fullscreen-transitions-20261027.md)

## 11. 무기 전환음과 잠금·복귀

무기를 바꿔도 소리가 나지 않는 경로에 효과음 호출을 연결했다. 잠금·백그라운드·오랜 무입력 상태에서는 게임을 멈추고 메뉴를 띄우도록 사용자가 요구했다.

앱 비활성화 때 전투·효과음·유지 입력을 정리하고, 돌아온 뒤 직접 재개하게 했다. 전투 중 무입력 120초도 같은 정지 경로를 사용한다. 사용자는 이후 소리가 동작한다고 확인했다. [생명주기 검사](../../Tests/iOS/HMPassiveLifecycleTests.mm), [실행 정책](../runtime-policy.md)

## 12. Mac 화면 대기와 시스템 연결 누수

공용 모듈과 Mac 앱을 추가한 뒤 화면 제출 대기와 누수 검사 실패가 나왔다. 화면 크기·Retina backing·표면 갱신을 조사하는 비교 창도 만들었다. 비교 창은 캡처 여백의 발생 위치를 구분하기 위한 진단 도구였다. 검사 도구의 실패를 게임 전체의 실패로 설명하면서 원인 구분과 작업 진행이 늦어졌고, 사용자는 실제 게임 검사부터 끝내라고 지시했다.

누수는 Mac 앱의 `com.apple.linkd.autoShortcut` 연결 3개에서 417개·20,016바이트로 검출됐다. ad-hoc 서명에는 팀 ID가 없었고 시스템 로그는 앱 등록을 거절한 뒤 AppIntents가 재시도한 사실을 보여줬다. 게임이 추가한 XPC·단축어 기능은 없었다. 개발 인증서로 서명한 일반·치트 앱에서 누수 0건을 확인했다. Apple Intelligence 설정은 바꾸지 않았다.

표시 경로도 수정해 Mac 33개 검사가 통과했고 여섯 장면 p95는 10.86~14.29ms였다. CUA 창 캡처에만 남은 흰 여백은 macOS 전체 화면 캡처와 대조했다. 실제 3840×2160 캡처에는 게임이 네 가장자리까지 표시됐다. [계측·서명·캡처 전 과정](apple-platform-progress-20261026.md)

## 13. CLI 서명 실패와 기기 연결

CLI 설치·서명이 실패한 상황에서 사용자는 앞서 Xcode로 앱이 실행된 사실을 지적했다. 한 경로의 오류를 빌드 전체가 불가능한 것으로 설명한 것이 문제였다.

성공했던 Xcode GUI 빌드와 CLI의 서명·팀·기기 상태를 분리해 확인하고 설치를 진행했다. 기기 잠금·연결·신뢰·무선 상태를 구분하는 절차를 남겼다. 이후 iPhone·iPad의 무선 설치와 LLDB 연결을 확인했다. [설치](build-and-install.md), [무선 절차](../wireless-device-workflow.md)

## 14. 다른 Mac에서 빌드할 자원 누락

사용자는 다른 사람이 저장소를 받아 빌드할 수 있는지 물었다. 소스가 있어도 로컬에만 있는 그림·음원·맵에 의존하면 clone으로 빌드할 수 없었다.

필요한 자원을 Git/LFS에 포함하고 파일별 크기·SHA-256을 기록했다. 별도 GitHub clone에서 일반·치트 빌드와 코어·Simulator 검사를 수행했다. 현재 문서 작업에서 자원 검사기를 다시 실행해 1,482개 해시가 맞는 것을 확인했다. [새 clone 검사](clone-build-20261026.md), [자원 검사 도구](../../tools/verify_build_resources.py)

## 15. 자동조준 C 보정의 탄환 변경

초기 자동조준에는 탄속·분산·비행 경로를 바꿔 명중을 보정하는 C 기능이 있었다. 사용자는 자동조준과 명중 보정을 왜 나눴는지, 모든 탄환을 한 점에 모으는지 물었다. 이후 C 삭제를 지시했다.

보정과 버튼을 제거하고 표적 선택·포신 조정만 남겼다. 일반 앱에도 같은 기능을 넣었다. 자동조준 OFF에서 사격이 바뀌었는지 확인하기 위해 추가 전 커밋과 20무기·3시드·420프레임씩 비교했다. 25,200프레임 기록은 바이트 단위로 같았다. [기능 설명](features.md), [삭제·비교 기록](auto-aim-ipad-20261027.md)

## 16. 새 항공기의 외형·크기·출현·연사

첫 VTOL 시안이 실제 모델과 달라 사용자가 재해석 이유를 물었다. 사진·도면으로 형태를 다시 확인해 그렸고, 채택 뒤에도 외곽선·길이·높이·후방 불꽃을 수정했다. 기존 배치를 교체하지 않고 새 기체를 추가하라는 조건은 원래 1,182항목의 대조 검사로 확인했다.

다음 전투기 3종은 사용자가 정식 앱에서 화면 안에 갑자기 나타나는 문제를 발견했다. 기체 전체를 화면 밖에서 생성하고 진입 중 발사를 막았다. 연사 증가는 요청에 따라 25%에서 10%로 낮췄다. 미사일 이동 속도 25% 증가는 유지했다. [VTOL 기록](vtol-art-and-loadout-20261027.md), [전투기 기록](lux-lunae-design-20261027.md)

## 17. 문서 상태·저장소·보고서 분산

코드에 들어간 기능이 문서에서는 미완료로 남거나, 보고서가 여러 주소로 흩어지는 문제가 있었다. 사용자는 문서·소스·앱이 서로 설명돼야 하고 모든 보고서는 한 사이트에서 찾아야 한다고 지시했다.

HeavyMach를 게임 허브 아래 독립 저장소로 분리하고 누락 파일을 전수검사했다. 기획·정본·분야 정책·코드·검사 연결은 `document-map.json`과 문서 검사기로 관리한다. 기능 브랜치는 develop에, develop만 main에 병합하고 main 병합 커밋에 태그를 단다. 현재 원고는 v0.12 상태로 갱신했으며 통합 보고서의 목차에서 연결한다. [문서 체계](../document-governance.md), [저장소 관리](../repository-management.md), [현재 상태](implementation-status.md)
