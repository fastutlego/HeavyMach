# 글쓰기와 말하기

사용자의 질문에 먼저 답하고, 독자가 알아야 할 결과와 행동을 앞에 쓴다. 모든 보고서, 게임 안의 텍스트, GitHub 문서, 진행·최종 답변, 설명·발표 원고에 적용한다. 사실·추정·계획·사용자 관측·직접 실행을 구분한다.

## 작성

- 최신 사용자 지시, 제공 원본, 프로젝트 정본을 먼저 대조한다. 단순 조회·인용 요청에서는 원문을 보존한다. 재작성 요청에서는 허용된 본문을 고치되 사실·수치·인용·화자의 목소리를 유지한다.
- 한 문단에는 중심 내용 하나를 쓴다. 익숙한 단어와 능동형 동사를 쓰고 배경·구현 상세는 필요한 설명 뒤에 둔다. 한국어에는 ASD-STE100의 명료성 원칙을 참고하며 인증된 영문 표준 문서라고 부르지 않는다.
- 무엇을 고쳤는지, 왜 고쳤는지, 어떤 결과를 확인했는지 쓴다. 완료한 작업과 남은 작업을 시점·대상과 함께 구분한다. 시간·비용·개선율·인과관계는 근거가 있을 때만 쓴다.
- 자기평가·변명·과장·추상적인 기여 약속·격언·선제적 면책을 뺀다. “분석→개발→테스트” 같은 일반 절차나 요구사항 재진술로 해결 방법을 대신하지 않는다. 내용이 없는 문장은 삭제한다.
- 사용자가 정한 일을 다시 고르게 하거나 사용자에게 넘기지 않는다. 질문에는 답부터 하고 필요한 근거와 실제 다음 조치만 덧붙인다. 짧은 대화에 제목·중첩 목록을 강제하지 않는다.

## HeavyMach 개발 배경 원고

HeavyMach 개발자의 변·README 소개·GitHub 회고·SaaS Apps·Mags는 `docs/developer-background.md`, `docs/RESTORATION.md`와 연결된 원문을 읽고 쓴다. 기술 학습·AI 실험만으로 시작 동기를 설명하지 않는다. 개인 경험·사용자 정정·확인된 작업 이력을 구분하고, 사용자가 아직 주지 않은 다음 문단이나 결론을 만들지 않는다. 사실 확인 메모·작성 규칙·AI 자기평가는 원고 본문에 붙이지 않는다.

## 원고의 화자와 작업 주체

GitHub 소개·회고·SaaS 인터뷰의 ‘나’는 프로젝트를 기획하고 직접 플레이한 개발자다. 개발자를 ‘사용자’나 ‘프로젝트를 시작한 개발자’로 부르지 않는다. Codex가 실행한 분석·구현·그림 제작·빌드·계측을 개발자의 직접 작업으로 바꾸지 않는다. 주체가 바뀌는 문장에서 이름을 밝히고, 같은 주어의 반복은 줄인다. 기능 설명은 기능·코드를 주어로, 조작 안내는 플레이어의 행동으로 쓴다. 원문 인용·대화·검사 로그와 작업 지침의 역할 명칭은 보존한다.

인칭 검사는 제목·도입·본문·표·이미지 설명·검색 설명·다운로드 원고를 포함한다. 단어 치환 뒤 문장 전체를 읽고 주어 생략, 간접화법, 일반 플레이어와 개발자의 혼동까지 확인한다.

## 공개 원고의 주제 범위

2026-10-27 사용자 지시: GitHub에 게시할 소개·설치·개발 과정과 SaaS Apps·Mags 원고에는 IPA 이야기를 넣지 않는다. 개발 동기, 현재 기능, 구현과 수정 내용, 설치 방법을 설명한다. 과거 분석 기록은 사실 확인 근거로 보존하며 공개 원고에 그대로 복사하지 않는다.

## GitHub·Apps·Mags의 범위

GitHub는 개발 동기·기능·설치·트러블슈팅·사용자의 지적과 시정 지시·추가 기능·검증·버전·남은 과제를 모두 다룬다. 개발 완료·개발 중·남은 과제와 검사 상태를 구분한다. Apps는 기술 설명, Mags는 매거진 인터뷰 형식이며 두 매체 모두 현재 기능과 시정 과정을 포함한다. 인터뷰 답변은 사용자 원문에 근거하고 새 질문은 질문안으로 구분한다. `docs/public/github-documentation-plan-20261027.md`와 집필 안내를 따른다.

## 기능 설계와 구조 설명

자동조준·신규 적은 기획 의도→사용자가 지정한 목표·조건→실제 코드·에셋 구현→후속 수정→검증 결과 순서로 쓴다. 사용자 요구와 구현자가 선택한 상세 수치를 구분한다. workspace·모듈화는 현재 프로젝트의 기술적 배경과 실제 의존 구조로 타당성을 설명하며 다른 프로젝트를 참고하라고 했던 경위는 쓰지 않는다.

## 기능을 과장하지 않는 표현

기능의 규모와 성격에 맞는 평범한 이름을 쓴다. 화면 회전·버튼 배치·버그 수정 같은 작업을 큰 성취, 문학적인 이야기, 교훈이나 선언으로 포장하지 않는다. 제목을 자연스러운 기능명으로 줄일 수 있으면 줄이고, 상태와 조건은 본문에 쓴다.

- “양쪽 가로 방향에서 화면과 입력을 맞춘다” → “가로 화면 회전 지원”.
- “사용자 지시가 바꾼 구현” → “수정 내역”.
- “원본을 유지하며 넓힌 타이틀과 슬롯” → “타이틀·슬롯 메뉴 확장”.
- “REA로 분석하고 아이폰에서 실행하기까지” → “REA 활용 내역”.

제목뿐 아니라 도입·본문·캡션·결말·대화 답변도 같은 기준으로 읽는다. 짧고 구체적이라는 이유만으로 통과시키지 말고, 작은 기능에 의미나 서사를 덧붙였는지 확인한다. 설명이 필요한 실제 원인·동작·수치·사용자 인용은 보존한다. 특정 단어나 모든 서술형 제목을 일괄 금지하는 규칙으로 적용하지 않는다.

## 글의 목적에 따른 적용

- **게임 UI·온보딩·오류·설명:** 플레이어가 할 행동과 실제 결과를 쓴다. 개발 과정·검수 상태·내부 정책을 화면 문구로 옮기지 않는다. 버튼의 실제 기능, 실패 조건, 저장·소비 결과와 대조한다. 원작 문구·이미지 텍스트 보존 조건은 해당 게임 정본을 따른다.
- **보고서·기술 문서·GitHub:** 문제→판단/수정→확인된 결과를 연결한다. 긴 회고는 상황과 맡은 범위를 필요한 만큼 설명한다. 사용자·도구·작성자의 기여를 구분한다. 코드·검사·관측 경로와 출처를 연결하고 기술 정보는 표·부록으로 정리한다.
- **계획·제안:** 확인된 문제에 대한 구체적인 방법과 선택 이유를 쓴다. 아직 측정하지 않은 일정·성과를 만들지 않는다.
- **말하기·답변·발표:** 첫 문장으로 질문에 답한다. 짧은 문장으로 설명하고 실제로 필요한 확인 사항만 묻는다. 사용자가 요구하지 않은 해명이나 태도 설명으로 답을 대신하지 않는다.
- **기존 사이트 수정:** URL·절 앵커·이미지·인용·다운로드 대응을 보존한다. 과거 수치를 현재 성능으로 바꾸지 않는다. 게시 대상과 접근 범위는 해당 프로젝트의 보고 지침과 현재 Sites 스킬을 따른다.

## 마감

작성자에게 주는 금지·검수 지침을 독자용 본문에 옮기지 않는다. “성과로 만들지 않는다”, “확인한 것으로 쓰지 않는다”, “이것을 주장하지 않는다” 같은 문장은 삭제하고 해당 기능의 실제 동작·수치·현재 상태를 쓴다. 계획 문서에는 할 일·산출물·순서를 쓰되 작성자의 준수 선언을 덧붙이지 않는다. 이 기준은 단어 검색 뒤 문장 전체를 읽어 적용한다.

전체 원고를 읽어 사용자가 물은 항목의 누락, 모순, 과장, 불필요한 자기설명을 고친다. 원본·수정본의 사실·수치·현재 상태를 대조한다. 웹·다운로드·저장소 원고를 함께 갱신한다. 실제 화면에서 긴 문장·표·모바일 배치를 확인한다. 형식 검사 통과만으로 문장 의미나 게임 기능이 검증됐다고 보고하지 않는다.

## 2026-10-28 본문·캡션 수정 기준

- 측정값을 어떻게 주장·판정·해석하지 말아야 하는지 독자에게 지시하는 문장은 본문에서 뺀다. 필요한 조건은 측정 대상·환경·수치·통과/실패로 직접 쓴다. 예: “이 수치를 실제 FPS로 환산하지 않았다” → “측정 대상은 오프스크린 draw 처리시간이었다.”
- 그림 캡션에는 보이는 기체·동작·변경점을 쓴다. “OS 전체 스크린샷은 아니다” 같은 방어적 설명을 덧붙이지 않는다. 캡처 방법·해상도·해시는 관련 증거 파일에 둔다.
- 수정 요청을 받으면 같은 문구가 나온 문장 외에도 README, 연결 문서, 보고 원고·캡션·다운로드와 생성 코드에서 같은 유형을 찾고 문맥별로 고친다. 인용 원문과 실제 동작을 설명하는 부정문은 보존한다.
- 저장소 공개 같은 상태가 바뀌면 방문자의 설치·다운로드 안내까지 갱신한다. 실제 진행 중인 확인 작업이 없으면 “확인 중”으로 쓰지 않는다.
- `python3 tools/check_publication.py`는 알려진 재발 문구와 공개 상태 문장을 검사한다. 그 결과를 문장 전체 검토와 함께 확인한다.

## 설치·구현 범위와 영상 설명

- 설치 문서는 독자의 시작 환경, 원본·의존성, 실행 순서, 예상 산출물과 오류 해결을 쓴다. 현재 코드가 실제 읽는 경로와 명령 옵션을 대조한다. 새 clone에서 실행하지 않은 절차를 검증 완료로 표시하지 않는다.
- 구현 범위는 제공 기능, 실제 확인한 기기·조건, 미구현·미검사를 구분한다. 사용자 플레이와 자동 검사·성능 계측은 각각의 출처를 유지한다.
- SaaS 집필 자료 정리는 `docs/public/publication-inventory.md`를 따른다. HeavyMach의 자료 정리 요청을 Apps·Mags 본문 작성 지시로 바꾸지 않는다.
- 플레이 영상에서 README 이미지를 만들 때는 `docs/media-publication.md`를 읽는다. 프레임·클립의 원본 해시와 타임코드를 보존하고 실제 화면에 근거한 캡션을 쓴다.
