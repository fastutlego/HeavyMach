# 모든 글쓰기의 문장·근거 적용

작성 전에 Candidate 허브의 `docs/canon/design-reference.md` §7.5·§7.5.2를 읽는다. Web 저장소에서 작업 중이면 허브는 한 단계 위에 있다. 독자와 글의 목적을 먼저 확인한다. 의원에게 전달하는 보고서는 개발을 모르는 사람이 읽는 글로 쓴다. 사용자의 최신 질문과 목적을 먼저 정리하고 원고를 쓴다. 조사 메모나 사용자에게 해명한 대화를 보고서에 붙이지 않는다.

독자가 결정할 내용을 앞에 쓴다. 무엇을 얻는지, 평소 사용에 무엇이 달라지는지, 비용·시간·불편, 전달할 정보와 그 용도, 의원과 작업자의 역할, 선택 가능한 방법을 해당 업무에 맞게 설명한다. 계정·인증 정보를 요청할 때는 어떤 작업에 왜 필요한지 밝힌다. 사용자가 정한 담당과 진행 방식을 따른다. 작업자 대행으로 정한 일을 독자에게 직접 하도록 돌리거나, 정해진 방식을 다시 고르게 하지 않는다. 본인 인증처럼 독자가 실제로 해야 하는 행동만 구체적으로 적는다.

본문은 사실·조건·조치로 쓴다. 불확실한 내용은 `확인할 항목`과 `담당자·확인 시점`으로 표현한다. 중요한 제한과 미확인 사실을 지워서 확정된 것처럼 만들지 않는다. 개발 용어가 꼭 필요하면 일상어 설명을 먼저 붙이고 상세 기술은 뒤로 옮긴다.

사용자가 이미 지시한 내용과 보존된 조사 원문을 먼저 대조한다. 계정 유형 등의 선택 이유를 요청하면 적합성을 설명하는 실제 출처를 짧게 인용하고 바로 옆에 링크를 붙인다. 출처의 설명과 이번 업무의 권장 판단을 구분한다.

초안 전체를 독자의 입장에서 다시 읽고, 아래 문장을 발견하면 내용을 고친 뒤 게시한다.
- 조사·검사·정책 준수의 성실성을 설명하거나 이전 답변을 변호하는 문장.
- `약속하지 않습니다`, `확대하지 않습니다`, `성공이라고 하지 않습니다` 같은 작성자의 태도 설명.
- 결정에 도움을 주지 않는 법무식 면책·중복 경고·자기참조, 과장된 선언과 상투적 결론.
- 요청한 업무와 관계없이 덧붙인 정보 보관 지침, 필수 여부 해명, 독자에게 설정 작업을 넘기는 대안.

예: `HTTP200만으로 성공이라고 하지 않습니다` → `본문·사진·영상이 원문과 같은지 확인합니다.` `총액0원을 약속하지 않습니다` → `계정 전환은 무료입니다. 서버 추가 요금은 사용량을 확인한 뒤 계산합니다.` 문구 치환에 그치지 않고 문단의 목적과 독자에게 필요한 정보를 검토한다.

수정 후 사용자가 물은 항목이 모두 남았는지 대조한다. 출처는 관련 설명 가까이 또는 주제별 참고 자료로 둔다. 편집 점검 내용과 실행 로그는 보고서 본문에 넣지 않는다. 기존 보고서를 고칠 때는 주소와 댓글 연결을 보존한다. 게시 요청이 있으면 실제 관리자에서 본문을 열어 수정 원고와 대조한다.

한 번에 이해하기 어려운 원고는 기술 문장의 단어만 바꾸지 말고 구조부터 다시 쓴다. 비용·변경되는 점·독자의 할 일·담당자의 할 일을 앞세우며, 같은 조건과 경고를 여러 절에 반복하지 않는다.
