# 원고·콘텐츠 작성 정본

상태: 현행 정본

발효: 2026-08-14

범위: 매거진, 인터뷰, Notes, Apps 설명, 번역, 챗봇 파생 콘텐츠

## 1. 권위와 상태

원고의 권위는 다음 순서다.

1. 사용자의 최신 명시 결정과 사용자 제공 원문
2. 사용자가 승인한 문면과 익명화·공개 범위
3. 저장소·운영 환경에서 현재 확인한 사실
4. 승인된 원고에서 생성한 코드·번역·챗봇·DOM 파생물
5. 초안, 연구, 과거 핸드오버, AI가 모사한 문체

`raw`, `draft`, `review-required`, `approved`, `published`, `historical`을 서로 바꾸어 부르지 않는다. `사용자 검수 전`, `[검수]`, `승인 대기`, `코드 미배선`, `Claude 모사`가 표시된 자료는 승인본이 아니다. 현재 Web 코드에 실려 있다는 사실만으로 사용자 원문이나 승인본이라고 주장하지 않는다.

## 2. 변경 경계

- 조사·비교·제안 요청은 쓰기·배선·게시 권한이 아니다.
- 기본 동작은 원문 보존이다. 이상한 대목을 발견하면 해당 문장과 구체적인 문제를 먼저 보고하고, 사용자가 그 부분의 수정을 허용한 뒤에만 최소 범위로 고친다. 욕설·직설·논지·리듬은 오류로 간주하지 않는다.
- 문장 추가나 콜아웃 지정은 기존 문장·인접 문단의 재작성 허가가 아니다. 새 문면의 창작은 명시적인 새 초안 작성 지시가 있을 때만 한다. `다듬기`, `개선`을 범위 없는 전면 윤문으로 확장하지 않는다.
- 사용자 원문, 직접 인용, 화자 목소리, 사실·수치·날짜·실명, 익명화 수준을 임의로 바꾸지 않는다.
- AI가 작성하거나 화자를 모사한 문장은 그 사실을 숨기지 않고 사용자 검수 전에는 본인 발화로 표시하지 않는다.
- 번역은 승인된 기준 언어에서 파생한다. 기준 언어와 다른 언어가 갈라지면 미완료로 보고한다.
- 이미지 생성은 비용과 별도 시각 승인 경계를 따른다. 원고 승인만으로 유료 생성이나 이미지 교체가 승인되지 않는다.
- 유료 생성 자산은 `제안 → 유료생성 승인 → 생성완료 → 사용자 시각승인 → 게시완료` 상태를 구분한다. job ID, 모델, seed, MIME, 크기, 픽셀 치수, SHA-256, 검수 결과와 게시 commit을 비밀값 없이 추적한다.
- 새 `public/visuals/**` 파일은 `generate-paid-visual` action이 있는 사용자 승인 기록 없이는 추가하지 않는다. 생성완료 상태만으로 Web 배선이나 게시 권한이 생기지 않는다.
- 외부 AI memory는 원문·승인 증거가 아니다.

### 2.1 공개 카피의 존재 목적

매거진, 인터뷰, Notes, Apps 설명, 공개 카드와 챗봇 파생 문면은 독자에게 실제 콘텐츠와 확인 가능한 사실을 전달한다. 자료 수집·검수·승인·저장·배포·AI 처리 절차를 독자에게 설명하는 운영 문서가 아니다.

공개 카피에 다음 유형을 새로 끼워 넣지 않는다. 기존 원문에서 발견했다는 사실만으로 삭제·순화할 권한은 생기지 않는다.

- **과잉 편집 메타카피**: 무엇을 어떻게 검수·편집했다는 자기설명
- **운영 프로세스 노출형 카피**: 관리자 승인, 상태값, 자동 게시, DB·챗봇·AI 반영 절차
- **방어적·자기참조적 문구**: 독자가 묻지 않은 내부 판단과 선제적 변명
- **면책성 카피**: `자동 판정하지 않는다`, `완료를 뜻하지 않는다`처럼 컴플라이언스 문체가 본문을 대신하는 상태

이 금지는 매거진·인터뷰·Notes뿐 아니라 Apps의 제목, dek, 본문, 번역, 공유 카드와 챗봇 파생 문면에도 똑같이 적용한다. 제품의 실제 보안·결제·규제 구현을 설명하는 문장은 기술적 사실이므로 금지 대상이 아니다. 금지하는 것은 내부 작업자가 자신을 방어하려고 공개 본문에 검수 상태, 승인 절차, 선제적 면책과 책임 회피를 끼워 넣는 행위다.

상투적인 역량 전이 문구, 근거 없는 연결 문장, 추상적인 기여 약속을 금지한다. “X 경험을 Y 업무에 연결하겠습니다”, “이 경험을 바탕으로 기여하겠습니다”처럼 관련성이나 기여를 선언하는 문장을 붙이지 않는다. 관련성을 설명해야 하면 공통된 문제와 실제 수행 행동, 이번 작업에 적용할 구체적인 방법을 쓴다. 추가할 사실이나 방법이 없으면 문장을 삭제한다. 같은 뜻을 다른 추상어로 바꾸지 않는다. 새로 작성하거나 수정하는 문면에 적용하며, 기존 사용자 원문·직접 인용은 보존한다.

허위 구체성, 상투적 절차 나열, 요구사항 재진술, 해결 방법 없는 요구사항 재진술을 금지한다. 작업량·기존 코드·의존성 등 산정 근거 없이 주차·기간·수치·세부 작업을 확정하지 않는다. “분석 → 개발 → 테스트 → 배포” 같은 일반 절차나 기술명·점검 항목의 나열로 제안을 채우지 않는다. 공고의 요구사항을 “구현하겠습니다·연동하겠습니다·점검하겠습니다”로 바꾸어 반복하지 않는다. 제안에는 확인한 문제와 그에 대한 구체적인 해결 방법·선택 이유를 쓴다. 근거가 없으면 구체성을 꾸미지 말고 해당 문장을 뺀다. 원문 인용과 내부 요구사항 목록은 보존하되 이를 해결안으로 내세우지 않는다.

### 2.1.1 과잉 수사화 금지

과잉 수사화된 단문형 카피, 잠언체, 경구체, 짧은 문장을 교훈이나 선언처럼 만드는 문체를 금지한다. 제목·소제목·본문·콜아웃을 포함한 프로젝트 작성 문면 전반에 적용한다. 단순한 사실이나 문제에 교훈적·비장한 느낌을 주려고 서사적 긴장이나 의미를 덧붙이지 않는다. 제목과 소제목은 구체적인 대상·문제·행동을 직접 표현한다.

이 규칙은 새로 작성하거나 수정하는 문면에 적용한다. 기존 사용자 원문·직접 인용은 원문 보존 원칙을 따르며, 이 규칙 추가만으로 기존 콘텐츠를 일괄 재작성하지 않는다.

### 2.2 사용자 목소리 비순화 원칙

- 사용자가 승인한 직설성, 독설, 공격적 비유와 화자의 리듬을 `안전한 기업 문체`, 채용 담당자용 자기소개, 법무 검토문처럼 순화하지 않는다.
- 사실 오류, 공개 범위와 익명화 경계는 바로잡되 필요한 최소 문장만 고친다. 사실 정정을 빌미로 논지와 말투를 다시 쓰지 않는다.
- 내부에서 고려한 평판·법률·컴플라이언스 판단은 사용자에게 편집 판단으로 보고할 수 있지만, 사용자가 선택하지 않은 선제적 변명이나 면책문으로 공개 카피에 옮기지 않는다.
- 강한 말투 자체는 스타일 위반이 아니다. 사용자 원문보다 무난하고 방어적인 문장으로 바뀌어 화자의 힘이 약해진 상태가 위반이다.
- 후보 문면을 만들 때 사용자 원문 또는 승인 문면과 의미·사실·공개 범위·말투를 나란히 대조한다. 거친 표현을 삭제하거나 대체하려면 사용자의 새 명시 결정이 필요하다.

보호 경로 승인 기록에는 `voicePolicy: preserve-user-directness-no-defensive-compliance-rewrite`를 둔다. 이 값이 없는 원고·Apps 카피 변경은 커밋할 수 없다. 알려진 검수 상태·운영 메타카피·면책 문구의 신규 추가는 `scripts/harness/validate-public-copy-style.mjs`가 작업 diff에서 차단한다. 문자열 검사가 잡지 못하는 의미 순화는 승인 문면 대조와 사람의 검수가 담당한다.

### 2.3 편집 권한과 좁은 스타일 예외

보호되는 콘텐츠 카피 수정에는 `voicePolicy`와 함께 다음 승인 필드가 필요하다.

```json
{
  "copyEdit": {
    "mode": "preserve",
    "sources": ["사용자가 제공한 원문 경로 또는 정확한 발화 참조"],
    "allowedChanges": ["사용자가 이번 작업에서 허용한 구체적인 변경"]
  }
}
```

`preserve`가 기본이며 `targeted`는 먼저 보고한 문제에 대한 사용자 수정 허가, `compose`는 명시적인 새 초안 작성 지시가 필요하다. 빈 출처·빈 허용 범위·미정의 mode는 차단한다. 이 필드의 구조 검증은 **의미상 편집 허가의 증명은 아니다**. 특히 TS/TSX 소스의 코드 변경과 문면 변경을 문자열 검사만으로 판정하지 않으므로 원문·후보·최신 사용자 지시의 사람 대조를 생략하지 않는다.

나쁜 카피를 인용해 비판하는 문장은 비판 대상과 같은 금칙어가 있어도 허용할 수 있다. 실제 필요한 UI 안전·오류·결제 안내, 사용자가 승인한 말투도 유지한다. 이때 승인 기록에 `styleExceptions: [{file, text, reason, use}]`를 넣고 `file`은 정확한 상대 파일 경로, `text`는 해당 추가 문구를 덮는 정확한 소스 조각, `reason`은 비어 있지 않은 사유, `use`는 `quotation`, `necessary-ui-warning`, `user-approved-voice` 중 하나로 한정한다. 파일 와일드카드·전체 파일 면제·일부 단어만 일치하는 예외는 허용하지 않는다. 서로 다른 일치 문구는 각각 예외에 포함되어야 한다.

예외는 추적·stage된 승인과 작업 파일이 일치하고 현재 branch·HEAD 및 경로·도메인·action이 맞아야 한다. 커밋된 task diff에 한해서만 작업 기준점부터 첫 콘텐츠 변경 커밋에 함께 있던 원래 승인 기록의 조상 관계를 검증해 재사용한다. 새 staged/working 변경에는 현재 HEAD의 승인이 필요하다. 기존 운영 승인 문면은 전수 재작성하지 않는다.

검사는 기존 콘텐츠 모듈 외에도 `src/**/*.tsx`의 인라인 UI 카피와 계약에 열거된 공개 Markdown/MDX 원고를 포함한다. 테스트 fixture와 내부 governance·handover 문서는 공개 문면이 아니므로 분리한다. 편집 메모·검수·승인 상태는 내부 기록에 남기고 본문에 붙이지 않는다.

과잉 수사화된 단문형 카피·잠언체·경구체와 짧은 문장을 교훈이나 선언처럼 만드는 문체는 §2.1.1에 따라 금지한다. 문자열 패턴의 `WARN`은 자동 탐지의 한계이며 문체 사용 허용을 뜻하지 않는다. A-not-B 대비와 그 밖의 상투적 수사는 원문과 의미를 대조해 판단한다. 패턴 일치만으로 기존 사용자 원문·직접 인용을 자동 삭제하거나 재작성하지 않는다.

운영·법적 설명이 실제로 필요한 경우 본문에 넓게 흩뿌리지 않고, 사용자가 승인한 별도 정책·주석·내부 문서로 분리한다. 문자열 검사는 알려진 문구의 재발만 막을 수 있으므로 문단의 존재 목적과 독자 효용은 사람이 의미 단위로 검수한다.

어드민 제안서와 외부 지원 문안은 이 원칙에 더해 `PROPOSAL_AUTHORING_CANON.md`의 프로젝트 관계·성과 귀속 규칙을 따른다.

## 3. 작업 절차

1. `contracts/content/content-authoring-contract.json`과 도메인 인벤토리에서 영향 경로를 찾는다.
2. 원자료, 현재 초안 상태, 사용자 승인 문면, 공개·익명화 경계를 구분해 작업 기록을 만든다.
3. 보호 경로를 수정할 때는 사용자 발화 범위와 `copyEdit`을 담은 승인 기록을 생성한다. 특정 문제 보고 → 사용자 허가 → 해당 부분만 수정 순서를 지킨다. `검토`, `확인`, `제안`을 `edit` 또는 `publish`로 기록하지 않는다.
4. 원고 변경과 관련 번역·코드·챗봇·공유 카드·DOM 기준본을 같은 작업에서 대조한다. 자동 재생성 결과가 원문을 덮지 않게 한다.
5. 원고 구조·시각 배치가 바뀌면 모바일·크로스브라우징 정본과 실제 화면을 함께 검증한다.
6. 게시 전 승인본과 실제 렌더 문면을 대조하고, 미검수 문구·누락 언어·의도하지 않은 실명·수치가 없음을 확인한다.
7. 이미지 작업은 실제 파일의 MIME·magic byte·치수·비율·경로 존재, placeholder 제거, alt, 확대 동작, 공유 JSON-LD와 대상 viewport 크롭을 별도 검사한다.
8. 공개 카피가 내부 운영·검수·승인·AI 절차를 설명하거나 면책문으로 본문을 대신하지 않는지 의미 단위로 확인한다.
9. 사용자 원문 또는 승인 문면과 후보를 대조해 직설성·독설·리듬이 기업형 안전 문구로 순화되지 않았는지 확인하고 `npm run content:style:check`를 통과한다.

### 3.1 원고 결과의 기본 납품: 검토용 웹링크

- 원고 결과는 사용자가 전문과 이미지를 직접 볼 수 있는 Sites 또는 호스팅된 HTML artifact 웹링크로 보고한다. 운영 사이트와 분리된 사용자 검토용 납품이며, 로컬 파일 첨부만으로 완료하지 않는다.
- 대상 원고 버전의 전문을 요약·생략·임의 윤문 없이 보존하고, 분량과 집계 기준, 목차, 실제 이미지와 확대 보기를 제공한다. 검토용 화면 구성 자체가 원문 수정 권한은 아니다.
- 사용자 제공 원본, 참고 이미지, 실제 생성·존재가 확인된 이미지, 아직 생성하지 않은 기획을 구분한다. 파일이 없거나 로딩이 확인되지 않은 것을 이미 생성·표시·검증했다고 보고하지 않는다. 미생성 기획은 계획임을 명시할 뿐 이미지 표시를 대신하지 않는다.
- 원고 승인 상태와 편집 메타는 검토 UI 라벨 및 내부 작업 기록에만 둔다. 원고 본문에 편집 설명을 추가하지 않는다. 검토 페이지에 초안을 올렸다고 운영 게시 승인본이 되는 것은 아니다.
- 기본 접근 범위는 사용자 본인 전용이다. 공개·링크 소지자·조직 공유 등 접근 범위를 넓히는 변경에는 별도 사용자 권한이 필요하다. 본인 전용을 구현하거나 확인할 수 없으면 임의 공개로 대체하지 않는다.
- 사이트 ID, URL, 대상 원고 버전, 실제 접근 범위, 전문·분량·목차·이미지 로딩 및 확대·사용자 접근의 검증 결과를 내부 기록으로 남긴다. 선언한 설정뿐 아니라 실제 링크의 접근과 렌더 결과를 확인한다.
- 접근이 실패하거나 확인되지 않았으면 링크 납품이 완료됐다고 주장하지 않는다. 실패 지점과 남은 조치를 보고하며, 로컬 HTML만 만든 상태를 웹링크 발행·납품 완료로 바꾸어 말하지 않는다.
- 이 지시는 검토 보고 페이지를 호스팅할 권한이지 `sass.studio` 운영 게시, 공개 범위 확대, 유료 이미지 생성 권한이 아니다. 각각의 기존 승인 경계를 유지한다.

### 3.2 매거진 편집 대조 — 원고·화면·검토본을 구별한다

새 호 작성, 기존 호 편집, 검토용 웹페이지 조판 전에는 대상 호의 기존 문면과 비교할 기존 호를 정하고 다음 세 층을 함께 읽는다. 문체 검사 통과는 편집 규칙 준수의 증거가 아니다.

- 원고 기록: `docs/interview-jy.md`, `docs/interview-jy-v02.md`, `docs/interview-jy-v03.md`의 관련 톤·문답·발문 규칙. 문서의 자기 선언이나 옛 경로는 현행 권위가 아니다. 한다체·번역 시제 등 관행은 참고하되, 최신 원문 보존 지시보다 우선하여 원문을 자동 정정하거나 욕설을 고상화하지 않는다. 특정 호의 특례를 전 호에 일반화하지 않는다.
- 콘텐츠 모델: `src/entities/content/interview.ts`의 대상·비교 호, `interview-attribution.ts`의 인터뷰어 귀속. 소제목·질문·답변·발문·메타·이미지 역할을 분리한다. 질문을 소제목으로 대체하거나 질문을 누락하지 않는다.
- 실제 표현: `InterviewIssue.tsx`와 `magazine/index.tsx`의 공용 렌더. 현재 운영 구현은 소제목→질문 라벨과 질문→답변 본문이며, 답변 앞에 별도 A 라벨을 넣지 않는다. 원고 기록에는 Q/A가 명시되어 있으므로 “A 구분이 전혀 없다”거나 “웹에도 A가 있다”고 일반화하지 않는다. 검토본의 A 표시 여부는 사용자 결정과 해당 납품 형식에 맞춰 별도로 기록한다. 설명용 “나의 답”을 독자용 라벨로 복제하지 않는다.

작성자는 내부 편집 대조표에 `referenceIssues`, `sourcePaths`, `sourceDocumentConvention`, `renderedConvention`, `candidateConvention`, `approvedDifferences`, `verifiedItems`를 남긴다. 대상 호와 실제 읽은 비교 호의 식별자·파일 및 근거 구간을 기록하고, 승인 없는 차이는 기존 방식으로 맞추거나 사용자에게 결정할 지점을 제시한다. 이 대조표는 원고 본문에 넣지 않는다.

`verifiedItems`에는 제목·질문·답변 구분, 인터뷰어 귀속, 답변 문체와 원문 보존, 발문·콜아웃, 캡션·이미지 상태, 숫자·인용 출처, 리뷰/운영 전달 차이를 포함한다. 운영 콘텐츠의 생 문자열 paragraphs에는 Markdown 강조가 그대로 노출되므로 조판 방식도 확인한다. 참조 사진·미생성 구상은 완성 이미지가 아니며, 검토본 배치는 운영 레이아웃 변경 승인도 아니다.

역할별 책임: root는 대조 기준과 허용 차이를 지정하고, `funnel-content`는 기존 호와 후보를 대조해 편집하며, `funnel-verifier`는 같은 근거로 독립 재검사한다. 작성자의 “같다”는 보고를 검증 증거로 재사용하지 않는다. 대조 기록이 없거나 문서와 화면을 혼동한 경우 편집 검증은 UNVERIFIED다.

자동 검사는 알려진 설명용 라벨의 재유입과 경로 라우팅·역할 어댑터 누락을 차단한다. 말투·발문 위치·의미 보존 등 전체 편집 품질을 정규식으로 판정했다고 보고하지 않는다. 기존 원고 전체를 새 금칙어에 맞춰 재작성하지 않는다.

### 3.3 발행 완료 검사 — 2026-09-08 누락 시정

- 매거진 공유 이미지의 헤드라인은 영문 표지를 사용한다. 9호 이후 한국어 기본 원고와 기존 영문 번역을 구별하고, 기본 표지가 한국어라는 이유로 카드 언어를 바꾸지 않는다. 근거는 2026-07-29 Notes 카드의 매거진·Apps 영문 규칙과 2026-09-09 사용자의 10·11호 한글 OG 오류 지적이다. `src/app/_share/share-content.test.ts`는 전 호 카드의 라틴 문자 및 9~11호 기존 영문 헤드라인 일치를 검사한다. 강의 카드는 기존 한국어 제목·라틴 키커 규칙을 유지한다. 카드 이미지의 언어와 지면·공유문 본문의 언어를 같은 것으로 판정하지 않는다.

- `contracts/content/magazine-translation-revisions.json`은 의미 대조를 마친 4언어 문면의 SHA-256을 보존한다. 원문 한 문장만 바뀌어도 재대조를 요구한다. 해시 갱신·검사 통과는 의미 검수가 아니며, 원문·번역을 실제 대조하지 않고 통과시키기 위해 해시만 재생성하지 않는다.

- 7호 이후 공개 호는 ko/en/ja/de의 표지·질문·답변·발문·pull quote·aside를 대조한다. 언어 선택이 동작하거나 한국어 fallback을 반환하는 것은 번역 완료가 아니다. 문단·발문 누락 및 기준 언어의 최근 추가 문면과의 의미 차이도 확인한다. 구조 검사는 `src/entities/content/interview-publication.test.ts`, 의미·말투는 원문과 번역 대조로 검수한다. 새 호도 ISSUES 등록만으로 검사 대상이 된다.
- OG 원료 매핑 검사는 이미지 실물 검사를 대체하지 않는다. `e2e/magazine-publication.spec.ts`에서 `/magazine/{slug}`와 `/m/{slug}` 메타데이터, 실제 OG HTTP 응답·PNG signature·1200×630 치수·브라우저 decode를 검사한다. 이미지는 직접 보고 제목·글리프·잘림을 대조한다. SNS 제공자의 실제 공유 미리보기와 캐시 갱신은 별도 확인 사항이다.
- 같은 E2E에서 4개 언어의 질문·본문·발문 전체를 실제 렌더와 비교하고 light/dark의 phone/tablet/desktop 폭에서 overflow를 검사한다. Google Chrome viewport 결과를 실기기 Safari 검증으로 보고하지 않는다.
- 해당 E2E는 `test:e2e:smoke`에 포함되어 `verify:release`에서 실행된다. 운영 반영 후에도 정확한 배포 SHA에 대해 동일 경로를 확인한다. 미실행·실패·번역 미완료가 있으면 발행 전체 완료로 보고하지 않는다. 핸드오버에는 원고, 번역, OG 데이터, OG 실물 시각 검사, 실제 SNS 공유 검사, 테마별 브라우저 검사를 나눠 PASS/FAIL/UNVERIFIED와 근거를 기록한다.

## 4. 롤백

- 초안은 새 버전으로 보존하며 사용자 원본을 덮어쓰지 않는다.
- 잘못 게시된 문면은 마지막 승인 커밋으로 새 revert 커밋을 만들고 파생물을 함께 되돌린다.
- 게시 후에는 저장소, preview, production의 실제 문면을 각각 확인한다.

## 5. 근거 자료의 지위
