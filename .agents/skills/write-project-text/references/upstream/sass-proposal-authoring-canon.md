# 제안서·지원 메모 작성 정본

상태: 현행 정본

발효: 2026-08-23

범위: `/admin/proposals`의 제안 본문·관련 경력·칸별 답안·내부 메모, Wishket 등 외부 플랫폼에 옮겨 적는 지원 문안, 이를 작성·보정하는 사람과 AI

## 1. 존재 목적과 권위

제안서는 기술 목록이나 작업 절차를 전시하는 문서가 아니다. 확인 가능한 경력을 어느 관계에서 수행했는지 밝히고, 그 증거가 현재 공고에 어떻게 연결되는지를 짧고 정확하게 설명하는 외부 제출문이다.

권위는 다음 순서다.

1. 사용자의 최신 명시 결정과 사용자 제공 사실
2. `RESUME_CAREER_CANON.md`가 통제하는 이력서·경력 정본
3. 실제 저장소·배포·운영·계약 관계에서 확인한 증거
4. 현재 공고 원문과 로그인 뒤 실제 지원 화면 계약
5. 제안 초안, 내부 메모, 과거 핸드오버, AI의 추론

AI는 초안 작성 수단일 뿐 경력의 관계·소유 범위·진행 상태를 새로 정할 권위가 없다.

## 2. 프로젝트 관계 분류

성과를 적을 때는 아래 관계 중 하나를 먼저 확정한다. 관계가 확인되지 않은 성과는 외부 제출문에 쓰지 않는다.

| 관계           | 현재 확인된 예                                                     | 허용되는 핵심 표현                                 | 금지되는 오인                               |
| -------------- | ------------------------------------------------------------------ | -------------------------------------------------- | ------------------------------------------- |
| 유료 프로젝트  | 최웅주 선거사무소, 롯데렌터카 장기렌터카 영업 담당자 의뢰 프로젝트 | 유료 프로젝트, 의뢰 프로젝트, 후속 개발·운영       | 회사의 전사 공식 발주라고 근거 없이 확대    |
| 재직 중 수행   | Certilife, GRAP, Kakao Enterprise                                  | 재직 중 담당, 팀·조직 안에서 개발·운영             | 단독 의뢰·사업 소유로 전환                  |
| 독자 사업 준비 | Grimoire                                                           | 사업 준비를 위한 자체 서비스, 1인 기획·개발·인프라 | 유료 클라이언트 납품이나 재직 경력으로 표현 |

`운영 중`은 배포·유지 상태를 말할 뿐 매출·수주를 뜻하지 않는다. `참여`, `담당`, `단독 구축`, `운영`, `납품`은 서로 바꾸어 쓰지 않는다.

## 3. 성과 귀속 불변식

외부 제출문에 들어가는 중요한 성과는 최소한 다음 다섯 요소로 역추적돼야 한다.

1. 관계: 유료 프로젝트 / 재직 중 수행 / 독자 사업 준비
2. 프로젝트: 실제 명칭 또는 플랫폼 규정에 맞춘 익명 표기
3. 소유 범위: 단독 / 공동 / 특정 기능 담당 / 외주 관리
4. 상태와 시점: 완료 / 운영 중 / 후속 개발 중 / 협의 중
5. 근거: 이력서 항목, 코드·배포·운영 증거 또는 사용자 확인

서로 다른 프로젝트의 성과를 `최근 프로젝트에서`나 `별도 프로젝트에서`라는 한 문장에 합치지 않는다. 한 문단에 여러 프로젝트가 필요하면 관계와 프로젝트 경계를 문장마다 다시 밝힌다.

## 4. 외부 제출문과 내부 메모의 경계

### 외부로 복사될 수 있는 필드

- `content`
- `careerNote`
- `answers`의 각 칸

이 필드에는 제출받는 사람이 알아야 할 경력·적합성·수행 계획만 둔다. 제안서 자체의 관리자 검수·승인, 저장 상태, 자동 제출 여부, 크롤링·AI 작성 절차, 작성자의 선제적 변명은 넣지 않는다. 공고가 요구하는 회원 관리자 승인·콘텐츠 게시·DB 저장 기능은 제품 요구사항이므로 구체적으로 설명한다.

### 내부에만 남기는 필드

- `resumeNote`: 사용한 이력서 항목과 근거 locator
- `clientNote`: 적합도, 미확인 조건, 익명화 결정, 사용자 판단이 필요한 위험

내부 메모에는 운영 절차를 기록할 수 있지만 외부 필드로 자동 복사하지 않는다. 비밀번호·토큰·쿠키·연락처·비공개 제3자 자료는 내부 메모에도 저장하지 않는다.

## 5. 금지 카피

허위 구체성, 상투적 절차 나열, 요구사항 재진술, 해결 방법 없는 요구사항 재진술을 금지한다. 작업량·기존 코드·의존성 등 산정 근거 없이 주차·기간·수치·세부 작업을 확정하지 않는다. “분석 → 개발 → 테스트 → 배포” 같은 일반 절차나 기술명·점검 항목의 나열로 제안을 채우지 않는다. 공고의 요구사항을 “구현하겠습니다·연동하겠습니다·점검하겠습니다”로 바꾸어 반복하지 않는다. 제안에는 확인한 문제와 그에 대한 구체적인 해결 방법·선택 이유를 쓴다. 근거가 없으면 구체성을 꾸미지 말고 해당 문장을 뺀다. 원문 인용과 내부 요구사항 목록은 보존하되 이를 해결안으로 내세우지 않는다.

상투적인 역량 전이 문구, 근거 없는 연결 문장, 추상적인 기여 약속을 금지한다. “X 경험을 Y 업무에 연결하겠습니다”, “이 경험을 바탕으로 기여하겠습니다”처럼 관련성이나 기여를 선언하는 문장을 붙이지 않는다. 관련성을 설명해야 하면 공통된 문제와 실제 수행 행동, 이번 작업에 적용할 구체적인 방법을 쓴다. 추가할 사실이나 방법이 없으면 문장을 삭제한다. 같은 뜻을 다른 추상어로 바꾸지 않는다.


외부 제출문에는 다음 유형을 두지 않는다.

- **과잉 편집 메타카피**: 무엇을 검수했고 어떤 방식으로 초안을 만들었다는 자기설명
- **운영 프로세스 노출형 카피**: 제안서 자체의 관리자 검수·승인, 상태값, 자동 제출·게시, 크롤러·AI 반영 절차. 수주할 제품의 실제 기능 설명과 구분한다.
- **방어적·자기참조적 문구**: 독자가 묻지 않은 한계·면책을 앞세우는 문장
- **컴플라이언스 문체의 침범**: `자동 판정하지 않는다`, `완료를 뜻하지 않는다`처럼 제품 약관·감사 문구가 지원 본문을 대신하는 상태
- **형식적 지원 선언**: `안녕하세요`, `지원드립니다`, `경험으로 지원합니다`, `적합하다고 생각합니다`처럼 지원 의사나 자기평가만 있고 수행 근거가 없는 도입부
- **근거 없는 능력 선언**: `할 수 있다`, `익숙하다`만 있고 어느 프로젝트에서 수행했는지 없는 문장
- **합성 경력**: 서로 다른 프로젝트의 기술·성과를 한 프로젝트에서 전부 수행한 것처럼 결합한 문장
- **금지 관계 용어**: `수탁`을 외부 필드에 쓰지 않는다. 확인된 사실에 따라 `유료 프로젝트`, `의뢰 프로젝트`, `재직 중 수행`처럼 자연스럽게 표현한다.

`공개 이력서에 명시되어 있지 않습니다`, `확인된 핵심 경력에 포함되지 않습니다`처럼
근거 문서의 상태를 설명하는 문장도 외부 메타카피다. 이력서에 없다는 사실로 실제 경험이
없다고 단정하지 않는다. 관련 경험을 묻는 조건부 질문에는 확인된 관련 수행 사실로 답하고,
경험 유무가 미확인이면 내부 메모에 남긴다.

필수 경력이 없는 공고는 적합 대상에서 제외하고 이유를 내부 메모에 남긴다. 자기 기술 숙련도나 경력을 발주자에게 확인해 달라고 쓰지 않는다. 범위·예산·데이터 등 발주자가 결정할 질문만 외부 원고에 쓴다. 기술 태그로 사용 기간을 만들거나 재직 기간을 특정 기술의 사용 연수로 치환하지 않는다.

구현에 사용할 기술과 지원자의 과거 실무 경력 요건은 다르다. 과거 경력을 명시적으로 요구하지
않은 구현 과업은 확인된 관련 기술 경험과 구체적인 미래형 계획으로 답할 수 있다. 검수기가
공고에 없는 경력 요건을 추가하지 않는다. 우대 경력을 필수로 확대하지 않으며, Java·Spring
경력이 필수인 공고를 React 키워드가 있다는 이유로 적격 처리하지 않는다.

Python 데이터 처리와 별도 Next.js LLM 작업을 Python AI 시스템 개발 실적으로 합치지 않는다.
SI·SaaS PM·PL 7년 이상처럼 확인된 담당 기간과 맞지 않는 필수 경력도 생성 전에 제외한다.
이 선별은 필수 과거 경력 문장에만 적용하며 우대사항이나 새로 구현할 과업에는 적용하지 않는다.
사용자 일정·투입 시간·회의 참석 여부만 묻는 필수 질문은 결정을 만들지 않는다. 내부 메모와
요구사항 대응에 해당 질문을 남기고 외부 답안은 비워 두며, 준비 완료 판정은 계속 차단한다.

## 6. 익명화 규칙

익명화는 출처 삭제가 아니다.

- 플랫폼이 회사명·외부 연락 수단을 제한하면 `지방선거 선거사무소 유료 프로젝트`, `대형 장기렌터카사 영업 담당자 의뢰 프로젝트`, `기업 협업툴 재직 개발`처럼 관계와 프로젝트 성격을 보존한다.
- 내부 메모에는 실제 프로젝트명과 익명 표기를 함께 기록한다.
- `롯데렌터카 프로젝트`를 회사 전사 발주로 오해시킬 수 있으면 `롯데렌터카 장기렌터카 영업 담당자가 의뢰한 프로젝트`로 관계를 한정한다.
- 익명화된 문장도 어느 성과가 어느 프로젝트에서 나왔는지 구분돼야 한다.

## 7. 작성 절차

1. 현재 공고 원문과 실제 지원 칸·글자수 제한을 다시 확인한다.
2. 사용할 경력마다 관계·프로젝트·소유 범위·상태·근거·외부 표기를 적은 근거표를 만든다.
3. 공고의 핵심 요구사항마다 가장 강한 근거 프로젝트를 연결한다. 요구사항이 서로 다르면 관련 프로젝트를 둘 이상 사용하며, 한 회사 경력을 모든 공고의 기본 근거로 반복하지 않는다.
4. 전환형 UI/UX·반응형 퍼블리싱·디자인 시스템 공고에는 장기렌터카 견적 퍼널과 최웅주 선거사무소의 정보 구조·시각 언어를 우선 검토한다. 네이티브 모바일 요구에는 Certilife를 우선 검토한다.
5. `가장 강한 직접 근거 → 추가 프로젝트별 수행 증거 → 이번 작업의 접근 → 착수 전 확인사항` 순으로 초안을 만든다. 첫 문장은 인사·지원 의사·자기평가가 아니라 관계·프로젝트·담당 범위·확인된 결과로 시작한다.
6. 외부 필드와 내부 메모를 분리한다.
7. 프로젝트 경계, 과장, 메타카피, 면책성 문체, 금지 관계 용어, 익명화 수준을 의미 단위로 검수한다.
8. 사용자 결정이 필요한 금액·시작일·고용 형태·실명 공개는 비워 두고 내부 메모에 남긴다.
9. 저장 전 실제 지원 칸과 글자수를 다시 대조한다. 자동 제출은 별도 명시 권한 없이는 하지 않는다.

상세 작업표와 예시는 `../docs/admin-proposal-authoring-workflow.md`를 따른다.

### STAR·CAR 기본 작성 전략

위시켓을 포함한 모든 외주 제안서·플랫폼 등록 문안·콜드메일·입사지원서·자기소개서와 이력서의 경험 서술에 적용한다. 짧은 문단은 CAR(문제→행동→결과), 과제·문제 해결·협업 경험의 긴 답안은 STAR(상황→과제→행동→결과)를 기본으로 한다. 상황을 길게 설명하기보다 본인이 한 판단·행동과 확인된 결과를 중심으로 쓰고 공고와 공통된 기술 문제 및 구체적인 적용 방법을 설명한다. 관련성을 선언하는 마무리 문장은 붙이지 않는다.

근거표에는 요구사항, 프로젝트·관계, 담당 범위, 문제·과제, 개인 행동, 확인된 결과, 출처·시점, 공고와의 연결을 둔다. 결과는 수치 외에도 출시·사용·운영 지속·실제 산출물이 될 수 있지만 코드 존재를 실사용으로 바꾸거나 진행 중인 일을 완료형으로 쓰지 않는다. 결과가 미확인이면 행동·산출물까지만 쓰거나 다른 사례를 고른다. 수치·개선율·인과관계를 만들지 않는다.

‘하겠습니다’만 반복하지 않고 확인된 수행 근거를 먼저 쓴다. 다만 수행 계획·지원 동기·일정·견적처럼 직접 답해야 하는 문항은 질문에 먼저 답하며 STAR·CAR를 억지로 적용하지 않는다. 실제 지원 칸·언어·분량이 우선이다. 외부 문안에 전략 이름·네 단계 표제·작성 절차를 붙이지 않는다. 배경과 상투적 도입을 줄이더라도 행동과 결과는 보존한다.

작성 스킬 정본은 허브의 `.agents/skills/compose-project-applications/SKILL.md`다. Web 세션은 로컬 `compose-project-applications` 진입 파일을 통해 해당 정본을 읽는다. 자동 작성기처럼 스킬 발견을 끈 실행에서도 이 정본의 전략을 적용한다. 이번 설정 변경 자체는 기존 원고 일괄 수정이나 외부 제출 권한이 아니다.

## 8. 완료 조건

다음을 모두 만족해야 `제안서 초안 준비 완료`라고 보고한다.

- 중요한 과거형 주장마다 프로젝트와 관계가 보인다.
- 경험 문단은 STAR·CAR에 따라 개인 행동과 확인된 결과가 드러나며, 미래형 약속만으로 공고 적합성을 대신하지 않는다.
- 첫 문장이 인사·지원 의사·자기평가가 아니라 가장 강한 직접 근거로 시작한다.
- 유료 프로젝트·재직·독자 사업 준비가 섞이지 않는다.
- 공고의 서로 다른 핵심 요구가 관련 프로젝트별 근거로 대응되며 한 회사 경력만 관성적으로 반복하지 않는다.
- 외부 필드에 금지 관계 용어가 없다.
- 여러 프로젝트의 성과가 한 프로젝트처럼 합쳐지지 않는다.
- 진행 중인 작업은 완료형으로 부풀리지 않는다.
- 외부 필드에 내부 운영·승인·AI 절차가 없다.
- 익명화 뒤에도 프로젝트 성격과 성과 귀속이 남는다.
- 글자수 초과와 고아 답안이 없다.
- 사용자 판단 항목과 미확인 사실이 내부 메모에 분리돼 있다.

문자열 센서는 알려진 재발을 잡는 최소 장치일 뿐이다. `최근 프로젝트`, `별도 프로젝트`, `할 수 있다`는 표현은 문맥에 따라 정당할 수 있으므로 기계적으로 금지하지 않고 사람이 프로젝트 귀속을 검수한다.

## 9. 집행 층과 남은 경계

- `canon-manifest.json`과 admin/content 계약이 이 문서를 현행 정본으로 등록한다.
- `manage-sass-records`과 `edit-sass-publications` 스킬이 제안서·공개 카피 작업의 진입점에서 이 규칙을 읽게 한다.
- `validate-domain-workflows.mjs`는 정본, 관계 분류, 외부·내부 필드 경계와 별도 제출 권한 규칙이 삭제되면 실패한다.
- 실제 제안 문안은 운영 DB에 있어 Git 정적 검사만으로 내용까지 검증할 수 없다. 현재 집행은 저장 전 근거표·체크리스트와 운영 데이터 읽기 점검을 함께 사용한다.
- 향후 어드민 저장 경계에 자동 검사를 추가할 때 명백한 운영 메타카피·면책 문구는 경고할 수 있지만, 프로젝트 귀속과 관계 분류는 정규식 통과 여부로 자동 승인하지 않는다. 사람의 의미 검수를 대체하지 않는다.
- 어드민 저장 경계는 형식적 인사·지원 선언과 알려진 운영 메타카피·면책 문구를 서버에서 차단한다. 이 차단은 명백한 재발만 막으며 프로젝트 귀속과 사실성을 승인하지 않는다.
- 예약 자동화의 작성기는 로컬 Codex CLI가 현재 ChatGPT 로그인을 재사용하는 비대화형 임시 세션이다. 운영 애플리케이션에 외부 모델 API 키를 추가하지 않는다.
- 작성기에는 공고 원문을 불신 입력으로 표시하고 승인된 근거표만 함께 전달한다. 운영 비밀 환경변수는 제거하며, 읽기 전용 임시 작업 디렉터리와 JSON Schema 출력으로 제한한다.
- 작성 모델은 `gpt-6-astra`, 추론은 `high`로 고정한다. 공개 `public/resume.html`의 전체 경력·기술을 읽고 연락처·주소를 제거한 근거와 해시를 전달한다. 네 가지 고정 경력 요약만으로 작성하지 않는다.
- Codex 결과는 자기검수 표시에 의존하지 않는다. 공고 ID, 허용 답안 키, 글자수, 금지 문체와 요구 인용→답안 인용→경력 출처를 검사한 뒤 별도 세션에서 의미 검수한다. 실패 시 한 번 고쳐 쓰며, 다시 실패한 공고만 저장하지 않는다. 다른 공고는 계속한다.
- 지원자 필수 요건이 개인사업자·법인사업자만 허용하면 사업자로 계약 가능한지에 대한 내부 자격 확인과 user-decision 대응을 작성기가 강제로 보존한다. 개인·팀도 허용하는 공고나 업무 설명의 사업자 언급을 같은 필수 자격으로 확대하지 않는다. 외부 문안에 이 확인 절차를 덧붙이지 않는다.
- 호스트 셸·브라우저·앱·플러그인·다중 에이전트 도구를 CLI 기능 설정으로 끄고 웹 검색과 호스트 스킬 발견도 끈다. 읽기 전용 sandbox를 OS 전체의 파일 읽기 격리라고 설명하지 않는다.
- 지원 폼이 파트너 필수 정보 등록 조건으로 잠겨 있어도 공고 전문 기반 원고는 작성한다. 가상의 지원 칸은 만들지 않으며 댓글 폼을 지원 폼으로 인정하지 않는다. `profile-required` 상태와 후속 재수집 필요를 내부 기록에 남긴다.
- 이전 자동 작성본은 본문·답안·내부 메모·메타데이터 지문이 일치할 때만 갱신한다. 수동 저장은 `[wishket-manual-edit]`를 남기고, 자동 저장 직전 DB의 기존 수정 시각·메모를 다시 대조해 경합 시 보존한다. 과거 지문이 보호하지 않았던 금액·기간 등은 업그레이드 후에도 보존한다.
- 공고·지원 칸·작성기 버전·모델·공개 이력서 해시가 같으면 재작성하지 않는다. 프로필 등록 때문에 지원 폼을 열지 못한 경우에도 공개 상세의 사전 검증 질문은 입력 지문에 포함한다. 지원자 수·조회 시각·주변 안내 문구는 제외한다. 요구사항 대조 기록은 어드민에서 재조회하며, 수동 수정 후에는 자동 작성 당시 기록임을 구분한다.
