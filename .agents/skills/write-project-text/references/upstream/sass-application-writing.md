# 실제 수행 경험으로 제안·지원 문안 쓰기

Sass 경력 사실은 [경력 정본](../ProjectPersonalFunnelPageWeb/governance/RESUME_CAREER_CANON.md), 제안문 기준은 [제안서 작성 정본](../ProjectPersonalFunnelPageWeb/governance/PROPOSAL_AUTHORING_CANON.md)을 따른다. 일반 계획·코드·문서 운영은 설치된 Agent Skills에 맡기며 이 스킬은 개인 수행 근거와 대외 문체를 담당한다.

## 근거를 먼저 고른다

공고의 요구, 실제 문항과 글자 수, 현재 이력서, 관련 프로젝트 자료를 읽는다. 원문을 조회하지 못했으면 확인한 범위를 구분하고 필수 문항이나 조건을 만들지 않는다. 해당 프로젝트의 경력 정본과 문체 규칙을 함께 따른다.

내부 작업표에 `요구사항 | 프로젝트·관계 | 내가 맡은 범위 | 문제·과제 | 행동 | 확인된 결과 | 출처·시점 | 이번 요구와의 연결`을 정리한다. 매번 같은 프로젝트를 쓰지 말고 공고에 가장 직접적인 근거를 고른다. 팀 성과와 개인 기여, 재직·유료 의뢰·자체 서비스를 구분한다.

## 분량과 문항에 맞게 STAR·CAR를 적용한다

- 짧은 제안 도입, 이력서 항목, 프로필·콜드메일은 **CAR: 문제 → 내가 한 행동 → 결과**를 기본으로 한다.
- 경험·문제 해결·협업을 묻는 긴 답안은 **STAR: 상황 → 맡은 과제 → 내가 한 행동 → 결과**를 기본으로 한다.
- 상황 설명은 짧게 하고 개인의 판단·행동과 결과를 중심에 둔다. 공고와의 관련성을 설명할 필요가 있으면 공통된 기술 문제와 구체적인 적용 방법을 쓴다. 경험 문단 끝에 연결·기여 선언을 관성적으로 붙이지 않는다.
- STAR·CAR는 내부 구성 도구다. 제출 문안에 영문 약어나 ‘상황/과제/행동/결과’ 표제를 기계적으로 붙이지 않는다. 회사가 정한 문항·형식·언어·분량이 우선이다.
- 지원 동기·일정·견적·개인정보처럼 경험 서술이 아닌 칸에 억지로 네 단계를 채우지 않는다. 수행 계획을 묻는 문항에는 미래형으로 직접 답하되 관련 경험이 있으면 짧게 연결한다.

## 미래의 약속보다 과거의 증거

‘개발하겠습니다’, ‘기여하겠습니다’, 기술명 나열만으로 본문을 채우지 않는다. 실제로 맡은 일과 확인된 결과를 먼저 제시하고, 앞으로의 접근은 공고가 필요로 하는 만큼 쓴다. 지원 동기나 계획만 요구한 문항은 질문에 먼저 답한다.

결과는 수치뿐 아니라 출시, 실제 사용, 문제 해결, 운영 지속, 납품 산출물일 수 있다. 실제 사용·배포 근거 없이 코드가 있다는 사실만으로 운영 성과라고 쓰지 않는다. 진행 중인 일은 현재 상태로 적는다. 결과가 없으면 확인된 행동·산출물까지만 쓰거나 더 적합한 사례를 고른다.

수치·개선율·매출·사용자 수·담당 기간을 만들지 않는다. 전후 수치나 인과관계가 없으면 ‘크게 개선’, ‘효율 극대화’로 대신하지 않는다. 이력서에 없다는 이유만으로 경험이 없다고 단정하지 않으며, 미확인은 내부 메모에 남긴다.

## 문체와 마무리

허위 구체성, 상투적 절차 나열, 요구사항 재진술, 해결 방법 없는 요구사항 재진술을 금지한다. 작업량·기존 코드·의존성 등 산정 근거 없이 주차·기간·수치·세부 작업을 확정하지 않는다. “분석 → 개발 → 테스트 → 배포” 같은 일반 절차나 기술명·점검 항목의 나열로 제안을 채우지 않는다. 공고의 요구사항을 “구현하겠습니다·연동하겠습니다·점검하겠습니다”로 바꾸어 반복하지 않는다. 제안에는 확인한 문제와 그에 대한 구체적인 해결 방법·선택 이유를 쓴다. 근거가 없으면 구체성을 꾸미지 말고 해당 문장을 뺀다. 원문 인용과 내부 요구사항 목록은 보존하되 이를 해결안으로 내세우지 않는다.

상투적인 역량 전이 문구, 근거 없는 연결 문장, 추상적인 기여 약속을 금지한다. “X 경험을 Y 업무에 연결하겠습니다”, “이 경험을 바탕으로 기여하겠습니다”처럼 관련성이나 기여를 선언하는 문장을 붙이지 않는다. 관련성을 설명해야 하면 공통된 문제와 실제 수행 행동, 이번 작업에 적용할 구체적인 방법을 쓴다. 추가할 사실이나 방법이 없으면 문장을 삭제한다. 같은 뜻을 다른 추상어로 바꾸지 않는다.


독자가 배경지식을 공유한다고 가정하지 않는다. 생소한 인물·회사·약어는 첫 등장에 정식 이름과 이번 사례에서의 역할을 함께 쓴다. 예를 들어 ‘AOC’만 쓰지 않고 ‘미국 연방 하원의원 알렉산드리아 오카시오코르테스의 2018년 선거 캠페인’, ‘Tandem’만 쓰지 않고 ‘해당 캠페인을 디자인한 스튜디오 Tandem’으로 소개한다. 이후에는 ‘해당 캠페인’, ‘이 스튜디오’처럼 문맥이 분명한 표현으로 받는다. 설명은 사례를 이해하는 데 필요한 만큼만 붙이고, 불필요한 약칭은 새로 만들지 않는다.

외부 문안에서 다음 실패가 보이면 그대로 전달하지 말고 고친다.

- ‘STAR 방식으로 정리했습니다’, ‘검증된 경험을 바탕으로’, ‘확인 가능한 근거로 작성했습니다’처럼 작성 방식이나 검증 상태를 소개하는 문장.
- ‘자동 판정하지 않습니다’, ‘완료를 의미하지 않습니다’, ‘사전 승인 후 진행합니다’처럼 지원서 자체의 운영·감사 절차가 본문을 차지하는 문장.
- 구체적인 수행 사실 없이 ‘기여하겠습니다’, ‘책임지겠습니다’, ‘최적의 솔루션을 제공하겠습니다’로 끝나는 문단.

이 문구를 ‘신뢰할 수 있는 역량’ 같은 추상적 자기평가로 치환하지 않는다. 해당 자리에 프로젝트·담당 행동·실제 결과를 쓰고, 쓸 사실이 없으면 문장을 뺀다. 공고가 요구한 제품의 승인 기능이나 실제 일정·업무 절차 설명은 이 금지와 구분한다. 단어 검색만으로 문체를 판정하지 않는다.


구체적인 설계·구현·연결·해결·운영 동사로 쓰고 추상적 자기평가와 AI 조사 설명·선제적 면책은 제외한다. 사용자 결정이 필요한 값은 지어내지 않는다.

검토 시 각 핵심 주장에 출처와 개인 기여가 있는지, 해당 문항에 답하는지, 결과와 미래 계획이 섞이지 않는지 확인한다. 글자 수가 부족하면 행동·결과를 보존하고 배경과 상투적 도입을 줄인다. 저장·발송·외부 지원은 해당 작업에서 받은 권한과 기존 운영 절차를 따른다. 이 스킬 설정만으로 기존 원고 일괄 수정이나 외부 제출을 실행하지 않는다.

## 크몽·위시켓 포트폴리오 수정

두 플랫폼의 프로젝트 내용은 운영 관리자 `/admin/portfolio`에서 먼저 조회한다. 최신 사용자 수정과 근거를 원본에 반영한 뒤 같은 버전을 두 플랫폼에 적용한다. 본문·이미지를 외부 페이지에서 재조회하고 플랫폼별 대조 기록을 저장한다. 한쪽만 바뀐 상태는 남은 플랫폼의 ‘수정 필요’ 상태로 유지한다. 상세 저장 체계와 CLI는 [Web 관리자 정본](../ProjectPersonalFunnelPageWeb/governance/ADMIN_OPERATIONS_CANON.md#포트폴리오-원본과-크몽위시켓-반영)을 따른다.
